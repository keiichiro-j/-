# YANASE 中古車管理システム 刷新 フェーズ1（スキャン精度検証）

企画書「YANASE 中古車管理システム 刷新企画書（フェーズ1：スキャン精度検証）」をコード化した Google Apps Script です。
AU・C7・MB の3社のスプレッドシートそれぞれに同じコードを入れ（コンテナバインド）、セットアップ画面で会社ごとに設定します。
フェーズ1ではアプリ画面は作らず、スプレッドシート上で「書類取込 → 取込待ちで確認・承認 → マスタへ転記」と「精度テスト」ができる状態にします。

## ファイル構成（企画書 第8章）

| ファイル | 役割 |
|---|---|
| `Code.gs` | メニュー、セットアップ、取込処理、検証・補正、転記、精度テスト、リンク付与、ログ |
| `Setup.html` | 初期セットアップ画面（会社名、フォルダ、APIキー、トリガー間隔など） |
| `Import.html` | 取込・精度テストの実行と進捗表示 |
| `Review.html` | 取込待ち行の確認画面（スキャン画像と読取結果を並べて表示。サイドバー／大画面の両方で使用） |
| `appsscript.json` | マニフェスト（タイムゾーン・権限） |
| `tests/run.js` | 補正・突合・採点など純粋ロジックの単体テスト（Node.js、追加依存なし） |

## 導入手順

1. **事前準備**
   - Gemini APIキーを再発行する（旧コードに直書きされていたキーは無効化する）
   - 対象スプレッドシートのバックアップを作成する（セットアップ実行時にも自動でコピーを作成します）
2. **コードを入れる**（3社それぞれのスプレッドシートで実施）
   - スプレッドシートの「拡張機能」→「Apps Script」を開き、`Code.gs`・`Setup.html`・`Import.html`・`Review.html` を同名で作成して内容を貼り付ける
     （clasp を使う場合は `clasp clone <スクリプトID>` した上でこのディレクトリの内容を `clasp push`）
   - プロジェクトの設定で「appsscript.json をエディタで表示」をオンにし、`appsscript.json` の内容に置き換える
3. **セットアップ**
   - スプレッドシートを開き直し、メニュー「★専用システム」→「初期セットアップ／設定変更」
   - 会社名・Gemini APIキーを入力して実行（初回は権限の承認が必要）
4. **販売済みシートの列統一**
   - セットアップ結果に「列配置がマスタと異なります」と出た場合は、メニュー「販売済みシートの列統一（移行ツール）」を実行
   - 対応表（標準の各列 ← 現行のどの列か）を確認してから実行します。移行前のシートは `販売済み_移行前_日時` として残ります
5. **計算式の動作確認** → **精度テスト** → **本番運用**（企画書 第9章の順）

## セットアップで作成・設定するもの

- シート：輸入車マスタ、国産車マスタ、販売済み（同一列構成）、取込待ち、精度テスト結果、ログ
  - 既存シートは上書きせず、足りない列だけを右端に追加します
- ステータス・区分のプルダウン（選択肢外の既存値は消さずに件数を報告）
- 見出し行と OCN 列の保護（警告表示のみ）
- 計算式の列：見出し行に ARRAYFORMULA を1つ置く方式へ切替。ただし各行に既存の式・値がある列は切替しません
- ドライブのフォルダ：受付、処理済み、エラー、車検証保管（既存フォルダのURL/IDも指定可）
- APIキーはスクリプトプロパティに保存（コードには書かない）
- 取込の定期実行トリガー（`scheduledImport`）

## 運用の流れ（企画書 第5章）

1. **スキャン**：注文書と査定書は1台分を1ファイルにまとめて受付フォルダへ。車検証は別ファイルで可
   （300dpi以上、グレースケールかカラー。電子車検証は「自動車検査証記録事項」をスキャン）
2. **取込**（定期実行、またはメニュー「受付フォルダの書類を今すぐ取込」）
   - 注文書＋査定書 → **仮登録**：OCN・仕入年月日を採番し、取込待ちに1行追加。ファイルは `OCN_元の名前` にして処理済みへ
   - 車検証 → **本登録**：車台番号 → 登録番号の順にマスタ・未転記の仮登録を探して紐付け。見つからなければ **紐付け待ち**
   - 読み取れなかった書類はエラーフォルダへ移動し、ログに記録
3. **確認**（メニュー「取込待ちの確認」）：要確認の項目は黄色で表示。修正して「承認して次へ」
   - シート上で直接修正し「承認」にチェックしても同じです
   - 紐付け待ちは「対象OCN」を入力して承認
4. **転記**（メニュー「承認済みをマスタへ転記」）
   - 仮登録 → 登録先マスタの末尾に1行追加（各行に式を入れている既存シートでは上の行の式を引き継ぐ）
   - 本登録 → 対象OCNの行に車検証の項目を反映し、車検証ファイルを `OCN.pdf` に改名して「車検証リンク」を付与
   - AIの読取値と確定値の差分は「確認修正」としてログに残ります（精度テストの「確認で直した件数」に集計）

## 精度を担保する仕組み（企画書 第6章）

| 仕組み | 実装 |
|---|---|
| 2エンジン照合 | Gemini の読取値が Drive OCR のテキストに現れるかを車台番号・登録番号・金額・走行距離で照合（`buildRecord`） |
| 推測させない指示 | プロンプトで「読めない項目は null・readable=false」を厳守させ、読取不可として要確認に（`GEMINI_PROMPT`） |
| 文字ルールによる補正 | 輸入車17桁の I/O/Q→1/0/0、国産車の連番の数字化、登録番号の桁・ひらがな・地域名一覧照合、日付の妥当性（`normalizeChassisNumber` `normalizePlate` `checkVehicleDates`） |
| 書類間の突合 | 車台番号・登録番号を車検証／査定書／注文書、仮登録済みの行とで照合し、一致数で信頼度（高・中・低）を判定 |
| 取込待ちシート経由 | AIの結果はマスタに直接書かず、承認済みの行だけを転記 |
| 手書き項目は確認必須 | 担当・区分・下取価格・下取充当額・仕入価格は常に「手書き確認」フラグ |
| 計算による矛盾検出 | 下取損（下取充当額−下取価格）がしきい値を超えたら警告 |
| 記録を残す | 取込・転記・修正・エラーをログシートに記録 |

## 精度テスト（企画書 第7章）

メニュー「精度テストを実行」。処理済み・車検証保管フォルダ（任意のフォルダも指定可）の書類を新しい順に指定件数読ませ、
入力済みの管理表（輸入車・国産車・販売済み）を正解として項目ごとに採点します。**マスタへの書き込み・ファイルの移動・改名は一切しません。**

- 照合キー：ファイル名先頭の OCN（`12345.pdf`・`12345_xxx.pdf`）、無ければ読み取った車台番号
- 出力（「精度テスト結果」シート）：項目別の件数・正答率・要確認に回った割合・**要確認なしの誤り（見逃し）**・確認で直した件数・判定（案）・誤りの例。M列以降に明細
- 判定（案）：活字項目は正答率98%以上で「自動反映（疑わしいものだけ確認）」、未満は「全件確認または改善して再テスト」。手書き項目は正答率にかかわらず人が承認

## 現行コードの課題への対応（企画書 第2章）

| 課題 | 対応 |
|---|---|
| 「ハイフンを含むものは型式」として国産車の車台番号を読み飛ばす | プロンプトで車台番号と型式を別欄として明示。国産車形式（`ZVW30-1234567`）を正しく扱う |
| AIの結果を検証せずそのまま書き込む | 取込待ちシート経由＋検証・補正・突合 |
| 読めない項目もAIに推測させている | 推測禁止・空欄＋要確認 |
| 査定書しか読み取らず車検証はリンクのみ | 車検証から初度登録日・満了日・登録番号・所有者・住所を読み取り本登録 |
| OCN が「NEW-乱数」になる | 既存の最大値と発行済み最大値から連番採番（スクリプトプロパティで重複防止） |
| 選択肢にない値の車両を編集すると空欄で上書き | 転記は必要なセルだけを書く。既存行のステータス・区分には触れない。プルダウンは選択肢外の値を消さない |
| 29列すべてを書き込む処理 | 項目ごとのセル書き込み。計算式の列・式の入ったセルは常にスキップ |
| 販売済みシートの列配置がマスタと異なる | 見出し名で列を特定＋列統一の移行ツール |
| 関数名不一致・重複定義 | 1ファイル構成に整理。`tests/run.js` で読み込み・主要ロジックを検証 |
| Gemini APIキーの直書き | スクリプトプロパティへ移動 |

## 未確定事項（企画書 第10章）とコード上の変更箇所

| 確認事項 | 変更箇所 |
|---|---|
| 現行「販売済み」シートの見出し行 | 移行ツールの対応表で確認。別表記は `FIELDS` の `aliases` に追加 |
| 計算式の列の一覧と式の内容 | `FORMULA_DEFS`（車検残・下取損は暫定式。買取金額は未定義のため設定しない） |
| 「買取金額」と「仕入価格」（AC列）が同じ項目か | 同じなら `FIELDS` から一方を外す、または `FORMULA_DEFS.buyPrice` を定義 |
| 注文書の記載項目 | `FIELD_SOURCES` と `GEMINI_PROMPT` の注文書の項目 |
| 電子車検証のスキャン対象（券面／記録事項） | 券面を検知すると警告を出す（`buildRecord`） |
| 精度テストに使う過去書類の保管フォルダ | 精度テスト画面で指定（既定は処理済み・車検証保管） |
| 判断基準（98%） | `ACCURACY_TARGET` と `summarizeAccuracy` |
| Gemini APIキーの再発行 | セットアップ画面で入力 |

## よくあるエラー：Gemini API の上限（HTTP 429）

「Gemini APIの上限」と出た書類は**エラーフォルダへ移さず受付フォルダに残し**、その回の取込を止めます（残りの書類で上限を消費し続けないため）。表示される上限の種類ごとの対処：

| 表示 | 原因 | 対処 |
|---|---|---|
| 1分あたりの上限 | 無料枠は1分あたり約10回 | 自動で待って再試行します。頻発する場合はセットアップの「Gemini呼び出し間隔」を長くする |
| 1日あたりの上限 | 無料枠の1日の回数を使い切った | 日本時間16〜17時ごろに戻ります。件数が多い運用・精度テストでは Google AI Studio で課金を有効にする |
| 無料枠がありません（上限0） | そのモデルに無料枠が無い、またはプロジェクトの無料枠が使えない | 課金を有効にするか、セットアップでモデルを変更する |

以前の版で上限エラーによりエラーフォルダへ移った書類は、メニュー「エラーフォルダの書類を受付に戻す」で戻せます。

## テスト

```bash
npm test
```

スプレッドシート・ドライブ・Gemini に依存しない純粋関数（車台番号・登録番号の補正、和暦日付・金額の解釈、OCN採番、
見出しによる列特定、ARRAYFORMULA の組立、書類の突合と2エンジン照合、精度テストの採点・集計）を Node.js の `vm` で検証します。
ドライブ・Gemini を使う取込・転記は、1社で試験導入する段階（企画書 第9章の3）で実データにより確認してください。
