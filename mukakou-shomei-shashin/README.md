# 無加工証明写真（Web版・動作確認用）

「無加工証明写真」アプリ企画書とワイヤーフレームをもとに、iOS（Xcode）実装に入る前の**動作確認・機能テスト用**に作った Web 版（Next.js）です。

## セットアップ

```bash
npm install
npm run dev
```

http://localhost:3000 をブラウザで開いてください。カメラ機能を使うため、スマートフォン実機でテストする場合は HTTPS（もしくは localhost）でのアクセスが必要です。

## 画面構成（ワイヤーフレームとの対応）

| 画面 | 実装 |
|---|---|
| ① 撮影画面 | `components/CameraScreen.tsx`（`getUserMedia` によるライブプレビュー、前後カメラ切替） |
| ②a 撮影直後の確認画面 | `components/ConfirmScreen.tsx`（アプリ内UIバッジのみ、画像は未加工） |
| ②b 保存・共有時に生成される画像 | `components/ExportScreen.tsx` + `lib/watermark.ts`（QR＋IDをピクセルに合成・常時ON） |
| ③ 証明情報 詳細画面 | `components/DetailScreen.tsx` |
| ④ 履歴（マイフォト）画面 | `components/HistoryScreen.tsx`（すべて／お気に入りタブ） |
| ⑤ Web検証ページ（外部） | `app/verify/[id]/page.tsx`（アプリ未インストールでもブラウザから確認可能） |

設定タブ（`components/SettingsScreen.tsx`）はワイヤーフレームに詳細がなかったため、証明のしくみの説明・ローカル履歴削除（テスト用）に加え、一般的なアプリ設定項目（お問い合わせ `/contact`・利用規約 `/terms`・プライバシーポリシー `/privacy`・バージョン情報）を追加しています。利用規約・プライバシーポリシーは条文プレースホルダーで、正式リリース前に法務確認が必要である旨をページ内に明記しています。

## 証明のしくみの実装

企画書 6章の7ステップに対応させています。

1. アプリ内カメラで撮影（`AVFoundation` 相当＝`getUserMedia`）
2. 固有ID発行（`UNEDITED-XXXX-XXXX`、`lib/id.ts`）・撮影日時を記録
3. 保存・共有操作時に、QR＋ID を画像ピクセルに合成（`lib/watermark.ts`）— **常時ON、オフ不可**
   - 写真の上に重ねるのはQRコードとID文字列のみで、背景・カード・ロゴは一切なし。写真の大部分は完全に透過したまま残ります。ID文字列は縁取り（アウトライン）付きで描画し、どんな写真の上でも視認できるようにしています。QRコード自体（の白黒モジュール）だけはコントラストが必須のため透過にしていません（後述）。
4. 合成後の最終画像（＝SNS等に流通する実ファイル）に、証明IDを埋め込んだPNGメタデータ（`tEXt`チャンク）を追加した上で SHA-256 ハッシュを算出（`lib/pngMetadata.ts`、`lib/hash.ts`）
5. サーバーが ECDSA (P-256) で電子署名（`lib/server/keys.ts`、`app/api/records/route.ts`）
   - 署名対象は「合成・メタデータ埋め込み後の最終画像」のハッシュのため、書き出し後に1ピクセルでも変化するとハッシュが変わり、検証で不一致になります（ハードバインディング）。
   - 画像本体はサーバーに保存されません。保存されるのは ID・ハッシュ値・署名・撮影日時のみ（`lib/server/store.ts`）。画像自体はブラウザの IndexedDB にのみ保存されます（`lib/history.ts`）。iOS版では PhotoKit 経由の写真ライブラリに相当します。
6. QRコードを読み取って `/verify/[id]` を開く、または `/verify` にIDを直接入力することで第三者が検証可能（QRを読み取れない環境でもIDだけで確認できます）
7. 検証ページでは署名の正当性チェックに加え、画像ファイルをアップロードしてハッシュ値の完全一致と、埋め込みメタデータ内の証明IDを確認できます（`components/VerifyUploadCheck.tsx`）

### QRコード部分を完全透過にしなかった理由

QRコードは背景とのコントラストが一定以上ないとスキャンできないため、QRモジュール自体を写真に対して半透明合成すると、実写真の内容次第で高確率で読み取り不能になります。そのため、QRコードとID文字列以外は一切描画せず、写真の残り部分は完全に透過のままにしています。QRコードは1:1ピクセルで描画（スムージング無効）し、実際にjsQRで複数回連続してデコードできることを確認済みです（後述）。

### 他アプリによる加工への耐性

見た目の透かし（QR＋ID）は、写真中の1つの矩形領域を切り抜く／塗りつぶすだけで除去できてしまいます。これに加えて、書き出し画像のPNGメタデータ（`tEXt`チャンク）にも証明ID等を埋め込んでいます（`lib/pngMetadata.ts`）。可視の透かし部分だけをクロップされても、単純なクロップ・フィルター加工ではメタデータまでは消えないため、検証ページはメタデータからも証明IDを回収し、「別のIDが埋め込まれている」「メタデータが見つからない」等を判定できます。ただし、JPEG再変換やSNSの再エンコード処理ではメタデータが失われることが多く、これは企画書にあるC2PA/Content Credentials等の業界標準と同様の限界です。改変そのものを検知できるのはあくまでハッシュ照合（ハードバインディング）であり、メタデータは「クロップされても証明IDだけは追跡できる」ための補助的な仕組みという位置づけです。

### ブランドロゴ・アプリアイコン

「UNEDITED」を国際展開を見据えた英語ワードマークとし（証明IDの接頭辞 `UNEDITED-XXXX-XXXX` とも一致）、カメラの絞り羽根（撮影）とチェックマーク（検証済み）を組み合わせたマークを作成しました（`lib/brandMark.ts` にジオメトリを一元定義）。

- `components/BrandMark.tsx` / `components/BrandLogo.tsx`：単色（`currentColor`）のインライン用マーク。確認画面のバッジや検証ページの見出しなど、白背景上での利用を想定。
- `lib/brandMark.ts` の `appIconSvgMarkup` / `components/AppIconPreview.tsx`：ダークグラファイトのグラデーション背景に、アクセントカラー（グリーン）のチェックマークを載せた、Apple純正アプリのアイコンに近い仕上げのアプリアイコン。`app/icon.svg`（ファビコン）と設定画面のプレビューに使用。

小サイズでは絞り羽根が視覚的に潰れて円+チェックのシンプルな形に収束するよう設計しているため、極小サイズでも視認性を保てます。QRコード内にはロゴを合成していません（QRのスキャン耐性を優先）。

## Vercelへのデプロイ

このリポジトリはモノレポ構成で、本アプリはサブディレクトリ `mukakou-shomei-shashin/` にあります。Vercelでプロジェクトを作成する際は、**Project Settings → General → Root Directory** を `mukakou-shomei-shashin` に設定してください（Framework Preset は Next.js のまま自動検出されます）。

### 永続ストレージ（Redis/KV）の接続（推奨・必須に近い）

サーバーは署名鍵と証明レコード（ID・ハッシュ・署名・撮影日時）を保存する必要がありますが、Vercelのサーバーレス関数はローカルディスクへの永続書き込みができません。**Redis/KVストアを接続しない場合、`/tmp` への一時保存にフォールバックしますが、インスタンスの入れ替わり（コールドスタート）のたびに署名鍵が再生成され、それ以前に発行したQRコードの検証が失敗するようになります。** 動作確認用途でも、QRコードを別デバイスでスキャンして検証する、という中心的な機能を試すには接続を強く推奨します。

1. Vercelダッシュボードのプロジェクト → **Storage** タブ → **Marketplace Database Providers** から Upstash（Redis）などのRedis互換ストアを追加
2. 追加すると環境変数が自動的にプロジェクトへ注入されます（`KV_REST_API_URL` / `KV_REST_API_TOKEN`、または `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` のいずれか）
3. 再デプロイすれば `lib/server/kv.ts` がこれらの環境変数を自動検出し、署名鍵・証明レコードの両方がRedis側に永続化されます（初回アクセス時に署名鍵を1つ自動生成し、以後使い回します）

環境変数を何も設定しない場合でも一応デプロイ・起動はできますが、上記の理由でQR検証が不安定になる点にご注意ください。ローカルの `npm run dev` ではこれまで通り `data/` ディレクトリへのファイル保存のみで動作します（Redis設定は不要）。

## Xcode（ネイティブ）移行時の対応表

| Web版で使用 | iOS版での対応 |
|---|---|
| `getUserMedia` | `AVFoundation` |
| Web Crypto (`SHA-256`) | `CryptoKit` |
| IndexedDB（`idb-keyval`） | `PhotoKit` の写真ライブラリ（証明対象は自アプリ撮影分のみ） |
| Next.js API Routes（署名・検証API） | 企画書7章のバックエンド（証明ID発行・検証サーバー） |
| Canvas合成（QR＋透かし） | Core Graphics / Core Image でのピクセル合成 |

ローカル開発では署名鍵・証明レコードは `data/`（gitignore 対象）にファイル保存されます。デプロイ時はRedis/KVへ保存されます（上記「Vercelへのデプロイ」参照）。本番運用ではさらに鍵管理（Secure Enclave / KMS 等）への置き換えが望ましいです。

## 動作確認済みの項目

Playwright（フェイクカメラデバイス）でのE2Eテストにより、以下を確認済みです。

- 撮影 → 確認 → 署名発行 → 透かし合成 → 保存/共有 の一連の流れ
- 証明情報詳細画面での署名の再検証（クライアント側で独立に検証）
- 履歴（IndexedDB）への保存、お気に入りタブでの絞り込み
- 撮り直し・カメラ切替後もカメラストリームが継続すること
- 外部の検証ページ（`/verify/[id]`）が正しい証明情報を表示すること、未登録IDでは「証明情報が見つかりません」と表示されること
- 検証ページでの画像アップロード照合：元の書き出しファイルは「一致」、1バイトでも改変すると「不一致」と判定されること（ハードバインディングの実証）
- IDを直接入力して確認する `/verify` ページ：不正な形式は送信前にエラー表示、小文字・前後空白を含むIDでも正しく `/verify/[id]` に遷移すること
- 透かしに合成したQRコードが、jsQR（ブラウザ実行）で複数回連続して正しくデコードできること
- 書き出し画像のPNGメタデータに証明IDが埋め込まれていること、検証ページへのアップロードでハッシュ一致とメタデータ内IDの一致が両方正しく報告されること
- `/contact` `/terms` `/privacy` ページが表示されること
