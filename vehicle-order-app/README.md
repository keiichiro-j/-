# 車両受注アプリ（GAS実装）

`b787266f-vehicleorderappproposal.docx`（車両受注アプリ 企画書）をベースにコード化した
Google Apps Script プロジェクトです。既存の車両在庫管理アプリ（本リポジトリのルート）・
新車売上在庫管理システムとは独立したシステムとして構築しています。

Google スプレッドシートをDBとし、GASの HTML Service でWebアプリ（カード形式の在庫掲示、
Hold（仮確保）、受注確定までを一元管理）を提供します。

Hold中の車両にはカード上に72時間の残り時間を進捗バー付きでリアルタイム表示し（毎秒更新）、
Hold・受注確定・在庫追加・設定保存の各操作はボタンを処理中表示にして多重送信を防止、
サーバー応答が一定時間ない場合はタイムアウトしてエラー表示に戻るため、操作後に画面が
固まって見える状態を防いでいます。

## データ構造（スプレッドシート3タブ構成）

車両情報の列（`VEHICLE_COLUMNS`、在庫リスト・受注リスト共通）:

| 列 | 内容 |
|---|---|
| 車種 / モデル / MP / ステア / 外装 / 内装 | 基本情報（ステアは 右・左 の選択式） |
| 有償オプション1〜7 | 有償オプションを7マス分確保 |
| コミッション | 車両ごとの一意なキー。数字のみの値（例: `0583911111`）でも、列を「書式なしテキスト」に
  設定しているため先頭の0が消えません（`applyTextColumnFormat_`）。既存シートで既に先頭0が
  消えてしまっている場合は `formatCommissionColumnsAsText_()` を一度実行してください（今後の
  入力分から有効。既に消えた値は自動では復元できないため手入力し直しが必要です） |
| 入港予定日 | 日付（入港予定日とVPCの間、P列） |
| 登録可能月 | `2026-08` のような年月。当月と一致する車両は画面上で「当月登録可能」バッジ表示されます |
| VPC | テキスト |
| 在庫開示 | 開示・非開示 の選択式 |

Hold（予約）・受注確定の共通入力項目（`HOLD_ORDER_INPUT_COLUMNS`、すべて必須）:

| 項目 | 内容 |
|---|---|
| リード番号 / 登録月 / 顧客 | テキスト |
| 担当者 | 入力不要。ログイン中のGoogleアカウントから、担当者マスタ（メールアドレス）を
  突き合わせて自動的に設定されます（詳細は「ログイン連携について」の項を参照） |
| 下取車の有無 / 保険加入の有無 | あり・なし の選択式 |
| OSS登録の可否 | 可・不可 の選択式 |

- **在庫リスト**シート: `INVENTORY_COLUMNS`。車両情報＋Holdステータス（available/hold）のみを保持します。
- **Holdリスト**シート: `HOLD_COLUMNS`。1台の車両につき 1st Hold・2nd Hold それぞれ最大1行
  （`コミッション`＋`順番`で一意）。上記の入力項目一式に加え、**担当者メール**（`staffEmail`。
  ログイン中のGoogleアカウントとの本人確認に使う識別キー。「担当者」欄はあくまで表示名）・
  開始日時・期限を保持します。車両情報とは別テーブルで管理し、一覧表示時に `commission` を
  キーに結合します（`attachHoldInfo_`）。
  - **2nd Holdの72時間は、1st Holdの72時間が終了した時点から起算**します（登録した瞬間からではありません）。
    1st Holdの期限が切れた時点で2nd Holdが存在すれば、Holdリストの当該行の「順番」を1stへ昇格させ、
    旧1st Hold行を削除します（`processExpiredHolds`）。
- **受注リスト**シート: `ORDER_COLUMNS`。受注確定時に在庫リストの行から車両情報を転記し、
  販売拠点・上記の入力項目一式（担当者メールを含む）・受注確定日時を追記します。在庫リストの
  該当行と、Holdリストの該当コミッションの行（1st/2ndとも）を削除します（二重管理防止）。
- 設定（テーマ・通知先メール・担当者マスタ）は Script Properties（`PROP_KEYS`）に保存します。

## ログイン連携について（重要な前提条件）

Hold登録・2nd Hold登録・受注確定・Hold解除の「担当者」は、**ログイン中のGoogleアカウントの
メールアドレス**から、担当者マスタ（後述）を突き合わせて自動的に決まります。担当者を
選ぶ・入力する操作は一切不要です。画面右上には、ログイン中の担当者名とメールアドレスが
常に表示されます（未登録の場合は警告表示）。

これが動作するには、**Webアプリのデプロイ設定が以下になっている必要があります**
（セットアップ手順5も参照）。

- 「実行するユーザー」: **アプリにアクセスするユーザー**（「自分」のままだと、誰が
  アクセスしても常にスクリプト所有者のメールアドレスが取得され、正しく動作しません）
- 「アクセスできるユーザー」: **同一Google Workspace組織内**、または利用者を個別に
  指定（「全員（匿名可）」のままだと、ログイン状態を取得できず常に未登録扱いになります）

上記の設定でも、担当者マスタに自分のメールアドレスが登録されていなければ「担当者情報を
取得できません」というエラーになり、Hold登録・受注確定・Hold解除は実行できません
（`requireCurrentStaff_`）。個人のGoogleアカウントのみで運用している、または
Workspace無しでの利用を想定している場合はこの仕組みが使えないため、その場合はご相談ください。

## 受注確定の権限

- **Hold中の車両は、Holdを行った担当者（現在の1st Hold担当者）のみ受注確定できます。**
  受注確定モーダルを開いた時点で、ログイン中のメールアドレスとHold担当者のメールアドレスが
  異なる場合は、その旨を警告表示したうえで受注確定ボタンをクライアント側でも無効化します。
  万一それを回避して送信されても、サーバー側 `canConfirmOrder_` が最終的に拒否します。
  Hold中なのにHold情報が取得できない（データ不整合）場合も、安全側に倒して受注確定は
  拒否されます。
- **Holdが入っていない車両は、ログイン中の担当者が誰であっても受注確定できます。**
- **本人確認は必ずメールアドレス（`staffEmail`）で行い、担当者の表示名（`staff`）は
  一切使いません。** 表示名は担当者マスタで後から変更され得る単なるラベルのため、
  名前同士の比較で本人確認をすると、担当者マスタの表示名を編集しただけで本人が自分自身の
  Holdを受注確定できなくなる不具合が起きます（実際に発生した不具合で、この方式に修正
  しました）。
- コミッションが数字のみの値（例:「2001」）の場合、Googleスプレッドシートへ貼り付けると
  自動的にNumber型のセルとして保持されることがあります。Holdリストとの結合・検索は
  `holdMatchesCommission_`（文字列化して比較）で行うため、型が揃っていなくても
  正しくHold情報が結合されます。

## Hold解除

在庫リストのHold中カードには、1st Hold・2nd Holdそれぞれに「解除」ボタンがあります
（顧客都合等でHoldを取り下げたい場合に使用）。

- **Holdを登録した担当者本人のみ解除できます。** 本人であるかどうかは、ログイン中の
  Googleアカウントの**メールアドレス**と、そのHoldの登録担当者の**メールアドレス**
  （`staffEmail`）を比較して判定します（表示名同士の比較ではありません。上記「受注確定の
  権限」および「ログイン連携について」を参照）。一致しない場合は解除モーダルに警告を表示し、
  解除ボタンをクライアント側でも無効化します。最終判定はサーバー側 `canCancelHold_` で行います。
- 1st Holdを解除した際に2nd Holdが登録されていれば、2nd Holdがそのまま1st Holdへ
  繰り上がります（繰り上がった時点から新たに72時間の期限が設定されます）。2nd Holdが
  なければ、その車両は在庫あり状態に戻ります。2nd Holdのみを解除した場合は、1st Hold
  はそのまま維持されます（`decideCancelAction_`）。

## 担当者マスタ

設定タブから担当者を登録できます（最大30人、`STAFF_LIST_MAX`）。**名前とGoogleアカウントの
メールアドレスの組**で登録してください（`{ name, email }`）。メールアドレスが、ログイン中の
Googleアカウントとの突き合わせに使われます（大文字小文字は区別しません）。メールアドレスが
重複する登録はできません。

- **1st Holdと同じ担当者は、2nd Holdを登録できません**（`canRegisterSecondHold_`）。
  クライアント側でも送信前に確認しますが、最終判定はサーバー側で行います。

## 元データスプレッドシート

`vehicle-order-app-master-data.xlsx`（チャットで送付済み）に、上記の列構成に合わせた
「在庫リスト」「Holdリスト」「受注リスト」「使い方」の4タブを用意しています。既存データは
このファイルの「在庫リスト」タブ・薄い青色のヘッダー列（車種〜在庫開示）へ貼り付けてください。
「Holdリスト」「受注リスト」タブはアプリが自動的に読み書きするため、手入力は不要です。

## セットアップ手順

1. **スプレッドシートの準備**
   - `vehicle-order-app-master-data.xlsx` をGoogleドライブにアップロードし、Googleスプレッド
     シートとして開きます（アップロード時に自動変換されない場合は「アプリで開く」→
     「Googleスプレッドシート」）。既存データは「在庫リスト」タブに貼り付けてください。
   - すでにお手元のスプレッドシートに既存データがある場合は、このファイルをテンプレートとして
     列構成・ヘッダーだけ合わせても構いません。
2. **claspでのデプロイ**
   ```bash
   npm i -g @google/clasp
   clasp login
   clasp create --type webapp --title "車両受注アプリ" --rootDir vehicle-order-app
   cd vehicle-order-app && clasp push
   ```
3. **スプレッドシートの紐付け**
   - 上記1で用意したスプレッドシートの「拡張機能」→「Apps Script」からスクリプトエディタを開き、
     コンテナバインドのスクリプトとして本プロジェクトのファイル一式を配置します（コンテナバインド
     であれば `SheetService.gs` の `getSpreadsheet_()` はそのまま動作します）。
     スタンドアロン運用する場合は `getSpreadsheet_()` を対象スプレッドシートIDでの `openById`
     に変更してください。
4. **トリガー設定**
   - GASエディタから `setupTimeDrivenTriggers_()` を一度だけ手動実行します
     （Hold期限チェック・5分毎）。
   - 既に運用中のスプレッドシートを使う場合、コミッション列の先頭0が消えてしまっている
     ことがあれば `formatCommissionColumnsAsText_()` も一度だけ手動実行してください
     （今後の入力分から先頭0が保持されます。既に消えてしまった値は手入力し直しが必要です）。
5. **Webアプリとして公開**
   - `clasp deploy` または GASエディタの「デプロイ」→「ウェブアプリ」。
   - **重要**: 担当者のログイン連携（「ログイン連携について」の項を参照）を使うには、
     デプロイ設定で「実行するユーザー」を **アプリにアクセスするユーザー** にし、
     「アクセスできるユーザー」を **同一Google Workspace組織内**（または利用者を個別指定）
     にしてください。「自分」のまま・「全員（匿名可）」のままだと担当者が正しく判定されません。
6. **設定画面での初期設定**
   - Webアプリの「設定」タブから、テーマ配色、Hold登録時／受注確定時のメール通知先を登録
     してください（通知先未設定の場合、メール通知はスキップされます）。
   - 担当者マスタ（最大30人）に、各担当者の**名前とGoogleアカウントのメールアドレス**を
     登録してください。ここに登録されていないメールアドレスでログインした人は、Hold登録・
     受注確定・Hold解除ができません。

## テスト

外部サービス（Spreadsheet/Mail等）に依存しない純粋ロジック（Hold・2nd Hold登録可否判定、
受注確定可否判定、Hold解除可否判定、全項目入力チェック、72時間経過時の昇格／解放処理、
Hold解除時の繰り上げ判定、コミッションの型不一致対策、検索・グループ化、担当者マスタの
正規化）を Node.js の `vm` サンドボックスで検証します。
