# 販売可能リスト（GAS実装）

`b787266f-vehicleorderappproposal.docx`（車両受注アプリ 企画書）をベースにコード化した
Google Apps Script プロジェクトです（アプリ名称は「販売可能リスト」）。既存の車両在庫
管理アプリ（本リポジトリのルート）・新車売上在庫管理システムとは独立したシステムとして
構築しています。デザインは指定のカラーパレット（メインネイビー#102A43／ダークネイビー
#0B1F33／ネイビーサブ#243B53／ブランドブルー#2F6FAE／ライトブルー#DCEAF7／ページ背景
#F4F7FA／カード#FFFFFF／ボーダー#D8E1E8／メイン文字#1F2933／サブ文字#6B7785）に基づく
「コーポレートネイビー」のカード型UI（高級輸入車ディーラー公式サイト風、以前は黒基調の
「ラグジュアリーブラック」→ 黄みがかった白基調の「ウォームアイボリー」を経て変更）で、
トップバー・比較バー・トースト通知だけはネイビー基調のまま統一して「額縁」の役割を
持たせています。グローバルナビは塗りつぶしのピル型タブではなく下線タブ、ボタンは
大文字＋レタースペーシングのピル型CTAという、公式サイトのページを思わせる見た目に
しています。設定タブからロゴ画像を登録できます。

見た目だけでなく人間工学的な使いやすさにも配慮しており、主要な文字色はWCAG AAの
コントラスト比（通常文字4.5:1以上）を満たすよう調整、モーダルの閉じるボタン等の
タップ領域は44×44px以上を確保、キーボード操作時にはタブ・ボタン・モデル写真タイルに
はっきりしたフォーカスリングが表示され、`prefers-reduced-motion`（アニメーション低減）
設定を尊重してホバー時の写真ズーム等を無効化します。

Google スプレッドシートをDBとし、GASの HTML Service でWebアプリ（カード形式の在庫掲示、
Hold（仮確保）、受注確定までを一元管理）を提供します。

Hold中の車両にはカード上に72時間の残り時間を進捗バー付きでリアルタイム表示し（毎秒更新）、
Hold・受注確定・設定保存の各操作はボタンを処理中表示にして多重送信を防止、
サーバー応答が一定時間ない場合はタイムアウトしてエラー表示に戻るため、操作後に画面が
固まって見える状態を防いでいます。

## データ構造（スプレッドシート5タブ構成）

車両情報の列（`VEHICLE_COLUMNS`、在庫リスト・受注リスト共通）:

| 列 | 内容 |
|---|---|
| モデル / MP / ステア / 外装 / 内装 | 基本情報（ステアは 右・左 の選択式）。**「車種」列は廃止**しており、モデルから列が始まります |
| 有償OP1〜7 | 有償オプションを7マス分確保。画面上は「、」区切りで表示されます |
| コミッション | 車両ごとの一意なキー。数字のみの値（例: `0583911111`）でも、列を「書式なしテキスト」に
  設定しているため先頭の0が消えません（`applyTextColumnFormat_`）。在庫リストへの新規登録
  だけでなく、**Hold登録・受注確定でHoldリスト／受注リストへ転記される際**、および
  **Hold登録時に在庫リスト側のHoldステータスを更新する際・2nd Hold昇格やHold解除で
  Holdリストの行を書き直す際**も、書き込み直前に対象セルの書式を明示的に
  「書式なしテキスト」へ再設定してから書き込むため、先頭0が消えません
  （`createHoldRow_` / `appendOrder_` / `updateInventoryVehicle_` / `updateHoldRow_`）。
  **不具合修正**: 以前は`updateInventoryVehicle_`・`updateHoldRow_`（既存行を丸ごと書き直す
  関数）にこの書式再設定が抜けており、その行のコミッションセルがまだテキスト書式に
  なっていない場合（列全体への一括書式設定を一度も実行していない既存シート等）、
  **Hold登録のたびに先頭0が消えてしまう**不具合があった。両関数にも同じ書式再設定を
  追加し、Hold登録・2nd Hold昇格・Hold解除のいずれでも先頭0が消えないようにした。
  既存シートで既に先頭0が消えてしまっている場合は `formatCommissionColumnsAsText_()` を
  一度実行してください（今後の入力分から有効。既に消えた値は自動では復元できないため
  手入力し直しが必要です） |
| 入港予定日 | 日付（入港予定日とVPCの間の列） |
| 可能月 | `2026-08` のような年月。当月と一致する車両は画面上で「当月登録可能」バッジ表示されます |
| VPC | テキスト |
| 在庫開示 | 開示・非開示 の選択式 |

Hold（予約）・受注確定の共通入力項目（`HOLD_ORDER_INPUT_COLUMNS`、すべて必須）:

| 項目 | 内容 |
|---|---|
| 販売拠点 / リード番号 / 登録月 / 顧客 | テキスト。販売拠点はHold登録時も含めて必須で、
  ログイン中の担当者が担当者マスタに登録している拠点名から自動的に入力されます（編集可。
  「担当者マスタ」の項を参照） |
| 担当者 | 入力不要。ログイン中のGoogleアカウントから、担当者マスタ（メールアドレス）を
  突き合わせて自動的に設定されます（詳細は「ログイン連携について」の項を参照） |
| 下取車の有無 / 保険加入の有無 | あり・なし の選択式 |
| OSS登録の可否 | 可・不可 の選択式 |
| 支払方法 | 現金・ローン の選択式 |

**入力は2ステップ**: Hold登録・2nd Hold登録・受注確定のモーダルは、8項目を一度に
出さず「ステップ1: 顧客情報（販売拠点・リード番号・顧客・担当者表示）」→
「ステップ2: 契約条件（登録月・下取車・OSS・保険・支払方法）」の2画面に分けています。
急いで入力するほど誤タップ・誤入力が起きやすいという現場の声を踏まえたもので、
ステップ1の必須項目が未入力のまま「次へ」を押すとエラーを表示して進めません。
担当者はログインアカウントから自動判定されるため、ステップ数が増えても入力の手間
自体は増えません。送信（`api_registerHold`等）はステップ2の最終送信時のみ行われ、
サーバー側の必須チェックは以前と変わらず全項目に対して行われます。

- **在庫リスト**シート: `INVENTORY_COLUMNS`。車両情報＋Holdステータス（available/hold）のみを保持します。
- **Holdリスト**シート: `HOLD_COLUMNS`。1台の車両につき 1st Hold・2nd Hold それぞれ最大1行
  （`コミッション`＋`順番`で一意）。上記の入力項目一式に加え、**担当者メール**（`staffEmail`。
  ログイン中のGoogleアカウントとの本人確認に使う識別キー。「担当者」欄はあくまで表示名）・
  開始日時・期限を保持します。車両情報とは別テーブルで管理し、一覧表示時に `commission` を
  キーに結合します（`attachHoldInfo_`）。
  - **2nd Holdの72時間は、1st Holdの72時間が終了した時点から起算**します（登録した瞬間からではありません）。
    1st Holdの期限が切れた時点で2nd Holdが存在すれば、Holdリストの当該行の「順番」を1stへ昇格させ、
    旧1st Hold行を削除します（`processExpiredHolds`）。
  - **既存シートへの影響（カレンダーイベントID列の追加）**: Holdリストの末尾に
    「カレンダーイベントID」列が追加されました（Googleカレンダー連携。後述）。既存の
    Holdリストシートを使っている場合、次にアプリが新しい行を書き込む際にこの列へ
    自動的に書き込まれます。既存シートの最終列の右隣に見出し「カレンダーイベントID」を
    追加しておくことをおすすめします（過去の行は空欄のままで問題ありません）。
- **受注リスト**シート: `ORDER_COLUMNS`。受注確定時に在庫リストの行から車両情報を転記し、
  上記の入力項目一式（販売拠点・担当者メールを含む）・受注確定日時を追記します。在庫リストの
  該当行と、Holdリストの該当コミッションの行（1st/2ndとも）を削除します（二重管理防止）。
- **変更履歴**シート: `AUDIT_LOG_COLUMNS`。Hold登録・2nd Hold登録・Hold解除（手動・自動）・
  受注確定のたびに1行追記します（更新・削除はしません）。列は 日時／操作／コミッション／
  モデル／担当者／担当者メール／詳細。時間主導トリガーによる自動処理（Hold自動解放・
  Hold自動昇格）は担当者欄に「システム（自動処理）」と記録されます。アプリ側に専用の
  閲覧画面はなく、スプレッドシートを直接確認する運用です。
- **Gクラス予約リスト**シート: `GCLASS_COLUMNS`（`VEHICLE_COLUMNS`＋担当者／顧客／リード番号の3列）。
  通常の在庫リストと同じ車両情報に、Q列「在庫開示」の右へR列「担当者」・S列「顧客」・
  T列「リード番号」を加えた表で、アプリ上は**閲覧専用**（Hold・受注確定の操作は一切
  ありません）です。受注リストと同様、データの追加・編集はスプレッドシートへ直接行う
  運用を想定しています。アプリのタブ順は ホーム／在庫リスト／受注リスト／
  **Gクラス予約リスト**／マイページ／設定です。
  - アプリでの表示は、受注リストと同じ考え方で**顧客名→担当者→モデル**の順に表示します
    （`gclassCardHtml_`）。自由検索（キーワード）はモデル・コミッション・リード番号に
    加えて**顧客名**でも一致します（`searchGClassReservations_`）。
  - 在庫リスト・受注リストと同様、カード表示・表（横列）表示を切り替えられます
    （`#gclassViewToggle`）。
  - **マイページにも表示されます**: Gクラス予約リストには（アプリの操作で自動設定される
    Hold・受注確定とは異なり）担当者メールアドレスの記録がないため、ログイン中の担当者
    本人の分だけを抜き出す際は、担当者マスタから解決した**表示名（担当者列のテキスト）**
    で突き合わせます（`staffNameMatches_`。Hold・受注確定のメールアドレス一致とは
    判定方法が異なる点に注意してください）。
  - **既存シートへの影響**: 以前のバージョンではT列に相当する位置に「リード番号」列のみが
    ありました。既存のGクラス予約リストシートを使っている場合は、「在庫開示」列の右隣に
    「担当者」「顧客」の2列を挿入し、既存の「リード番号」列がT列（担当者・顧客の2列分
    後ろ）になるようにしてください。
- 設定（テーマ・ロゴ・モデル写真・通知先メール・Google Chat通知先Webhook URL・担当者マスタ）は
  Script Properties（`PROP_KEYS`）に保存します。

**既存シートへの影響（販売拠点の列位置）**: 販売拠点は以前は受注リストだけの列でしたが、
Hold登録時にも入力・保存するようになったため、共通入力項目（`HOLD_ORDER_INPUT_COLUMNS`）の
先頭に移動しました。受注リストの列順は変わりません（元々「販売拠点」が車両情報の直後にあり、
共通入力項目の先頭に来ても位置は同じため）。一方、**Holdリストシートには新しく「販売拠点」列が
追加**され、以降の列（担当者メール・開始日時・期限）が1列分後ろにずれます。既存のHoldリスト
シートを使っている場合は、「順番」列の右隣に「販売拠点」の列を1つ挿入してください
（進行中のHoldがなければ、そのまま新しい列構成で運用を始めても問題ありません）。

## ログイン連携について（重要な前提条件）

Hold登録・2nd Hold登録・受注確定・Hold解除の「担当者」は、**ログイン中のGoogleアカウントの
メールアドレス**から、担当者マスタ（後述）を突き合わせて自動的に決まります。担当者を
選ぶ・入力する操作は一切不要です。画面右上には、ログイン中の担当者名とメールアドレスが
常に表示されます（未登録の場合は警告表示）。

これが動作するには、**Webアプリのデプロイ設定が以下になっている必要があります**
（セットアップ手順5も参照）。

- 「実行するユーザー」: **アプリにアクセスするユーザー**（「自分」のままだと、誰が
  アクセスしても常にスクリプト所有者のメールアドレスが取得され、正しく動作しません）
- 「アクセスできるユーザー」: **同一Google Workspace組織内**、または利用者を個別に
  指定（「全員（匿名可）」のままだと、ログイン状態を取得できず常に未登録扱いになります）

上記の設定でも、担当者マスタに自分のメールアドレスが登録されていなければ「担当者情報を
取得できません」というエラーになり、Hold登録・受注確定・Hold解除は実行できません
（`requireCurrentStaff_`）。個人のGoogleアカウントのみで運用している、または
Workspace無しでの利用を想定している場合はこの仕組みが使えないため、その場合はご相談ください。

**重要（修正済み）**: `appsscript.json` の `webapp.executeAs` が誤って `USER_DEPLOYING`
（実行するユーザー: 自分）になっていたため、上記の必須設定と矛盾していました。
`USER_ACCESSING`（実行するユーザー: アプリにアクセスするユーザー）に修正済みです。
**この修正を反映するには、GASエディタから新しいデプロイ（またはデプロイの管理→既存の
デプロイを編集して新しいバージョンを選択）を作成し直す必要があります。** マニフェストの
変更だけでは、既存のデプロイURLの動作は自動的には切り替わりません。

## 受注確定の権限

- **Hold中の車両は、Holdを行った担当者（現在の1st Hold担当者）のみ受注確定できます。**
  受注確定モーダルを開いた時点で、ログイン中のメールアドレスとHold担当者のメールアドレスが
  異なる場合は、その旨を警告表示したうえで受注確定ボタンをクライアント側でも無効化します。
  万一それを回避して送信されても、サーバー側 `canConfirmOrder_` が最終的に拒否します。
  Hold中なのにHold情報が取得できない（データ不整合）場合も、安全側に倒して受注確定は
  拒否されます。
- **Holdが入っていない車両は、ログイン中の担当者が誰であっても受注確定できます。**
- **本人確認は必ずメールアドレス（`staffEmail`）で行い、担当者の表示名（`staff`）は
  一切使いません。** 表示名は担当者マスタで後から変更され得る単なるラベルのため、
  名前同士の比較で本人確認をすると、担当者マスタの表示名を編集しただけで本人が自分自身の
  Holdを受注確定できなくなる不具合が起きます（実際に発生した不具合で、この方式に修正
  しました）。
- **不具合修正（メールアドレスの表記ゆれで本人が受注確定・解除できなくなる不具合）**:
  `canConfirmOrder_` / `canCancelHold_` / `canRegisterSecondHold_`（HoldService.gs）は、
  以前は`===`/`!==`でメールアドレスを厳密比較していたため、Holdリストの`staffEmail`列に
  前後の空白や大文字小文字の違いが混じっていると、本人であっても受注確定・Hold解除が
  拒否されてしまう不具合があった（実際に「Holdを行った担当者（◯◯）のみ受注確定できます」
  というエラーが本人にも表示される形で発生）。原因は、シートの行をオブジェクトへ変換する
  `rowToObject_`がセルの値をtrim・小文字化せずそのまま返す一方、`requireCurrentStaff_`は
  毎回trim・小文字化した値を返すため、Holdリストの`staffEmail`列がスプレッドシート側で
  直接編集される等して表記ゆれを含んでいた場合に両者が食い違うこと。クライアント側には
  既に表記ゆれを吸収する`emailsMatch_`があったが、最終判定を行うサーバー側の比較には
  同等の仕組みが無かった。サーバー側にも同じロジックの`emailsMatch_`（HoldService.gs）を
  追加し、3箇所すべての比較をこちらに置き換えて修正した。
- コミッションが数字のみの値（例:「2001」）の場合、Googleスプレッドシートへ貼り付けると
  自動的にNumber型のセルとして保持されることがあります。Holdリストとの結合・検索は
  `holdMatchesCommission_`（文字列化して比較）で行うため、型が揃っていなくても
  正しくHold情報が結合されます。
  - **不具合修正（クライアント側の比較機能でも同じ型不一致が起きていた）**: 車両比較機能
    （`toggleCompare_` / `isComparingCommission_` / `findVehicleByCommission`）は、
    サーバーから届いた車両データの `commission`（Number型になっていることがある）と、
    HTML要素の`data-compare`属性値（常に文字列）を`===`で直接比較していたため、型が
    一致せず「この車両の情報が見つからないため比較に追加できません」というエラーになる
    不具合があった。クライアント側にも`commissionEquals_`（文字列化してから比較する
    ヘルパー）を追加し、`holdMatchesCommission_`と同じ考え方で型の違いに影響されない
    ようにした。

## Hold解除

在庫リストのHold中カードには、1st Hold・2nd Holdそれぞれに「解除」ボタンがあります
（顧客都合等でHoldを取り下げたい場合に使用）。

- **Holdを登録した担当者本人のみ解除できます。** 本人であるかどうかは、ログイン中の
  Googleアカウントの**メールアドレス**と、そのHoldの登録担当者の**メールアドレス**
  （`staffEmail`）を比較して判定します（表示名同士の比較ではありません。上記「受注確定の
  権限」および「ログイン連携について」を参照）。一致しない場合は解除モーダルに警告を表示し、
  解除ボタンをクライアント側でも無効化します。最終判定はサーバー側 `canCancelHold_` で行います。
- 1st Holdを解除した際に2nd Holdが登録されていれば、2nd Holdがそのまま1st Holdへ
  繰り上がります（繰り上がった時点から新たに72時間の期限が設定されます）。2nd Holdが
  なければ、その車両は在庫あり状態に戻ります。2nd Holdのみを解除した場合は、1st Hold
  はそのまま維持されます（`decideCancelAction_`）。
- **不具合修正（変更履歴の記録失敗がHold解除自体を失敗させていた）**: 変更履歴
  （`appendAuditLog_`）への記録は、Hold登録・Hold解除・受注確定の本体処理が完了した
  「あと」に呼び出している。ここが例外を投げると、実際にはHold解除自体は成功して
  いるにもかかわらず、画面にはエラーとして表示されてしまう不具合があった。
  `appendAuditLog_` を try/catch で囲み、記録に失敗しても本体の処理結果には影響しない
  よう修正済み。
- **1st Hold・2nd Holdの両方が埋まっている車両は色を変える**: 通常のHold中（オレンジ）
  とは別に、2nd Holdまで登録済みの車両は赤系の色（カード左端の帯・バッジとも）で
  表示され、「これ以上の受け皿がない」状態がひと目でわかるようにしている。

## 管理者限定のデモカーHOLD・他店HOLD

管理者権限を持つ担当者（`SYSTEM_ADMIN_EMAILS`、後述「システムマスタ」参照）がログインして
在庫リストの「Hold」ボタンをタップした場合のみ、通常のHoldに加えて次の2種類のHoldを
選べます（`HOLD_TYPE`、`HoldService.gs`）。2nd Hold・受注確定にはこの選択画面は出ません。

- **デモカーHOLD**: リード番号・登録月のみの入力欄（どちらも未入力のままHold登録できます）。
  展示・試乗用のデモカーを在庫から確保しておくためのHoldです。
- **他店HOLD**: 販売店のみの入力欄（未入力のままHold登録できます）。他店舗での販売用に
  在庫を確保しておくためのHoldです。

どちらも次の点が通常のHold・2nd Holdと異なります。

- **Hold期限が無期限**です（`expiresAt`がnull。72時間の自動解放・自動昇格の対象になりません）。
  Googleカレンダーへのリマインドイベントも作成しません。
- 通常のHold（オレンジ）・2nd Hold（レッド／ブルー）とは異なる**専用の特別色**（紫系、
  `--hold-special`）で、バッジ・カード左端の帯・Hold詳細ブロックいずれも表示されます。
  期限表示欄は「無期限」の固定表示になります。
- 管理者権限のチェックはサーバー側（`normalizeHoldType_`）で行うため、非管理者が
  API呼び出しを直接操作してデモカーHOLD・他店HOLDを登録しようとしてもエラーになります
  （クライアント側の表示制御はUIの見た目を切り替えるだけで、信頼境界ではありません）。
- Hold解除・（Hold中の車両への）2nd Hold登録・受注確定は、通常のHoldと同じ操作方法・
  権限判定のままです（Holdを登録した担当者本人＝管理者のみが解除できます）。

## Googleカレンダー連携

Hold登録・2nd Hold登録を行うと、期限（72時間後）のリマインドイベントが**登録した
担当者本人のGoogleカレンダー**（デフォルトカレンダー）に自動的に作成されます
（`CalendarService.gs`）。期限の3時間前にもポップアップ通知が届くよう設定されるため、
うっかりHoldを失効させてしまうのを防げます。Hold解除・受注確定を行うと、対応する
カレンダーイベントは自動的に削除されます。

- **仕組み**: Hold登録・2nd Hold登録・Hold解除・受注確定はいずれも、担当者本人が
  Webアプリを操作するその場で実行されます。デプロイ設定「実行するユーザー: アプリに
  アクセスするユーザー」（`executeAs: USER_ACCESSING`）により、これらの処理は常に
  「今操作している担当者本人」として動くため、`CalendarApp.getDefaultCalendar()` は
  自動的にその担当者自身のカレンダーを指します。担当者マスタのメールアドレスを使って
  他人のカレンダーを直接操作しているわけではなく、担当者間でカレンダーを共有する設定も
  不要です。
- **初回利用時の許可**: Googleカレンダーへのアクセス（`calendar.events`スコープ）が
  新たに必要になったため、各担当者は初めてHold登録操作を行う際に、Googleの許可画面が
  表示されることがあります。
- **既知の制約**: Hold期限切れの自動処理（時間主導トリガー）は特定の担当者としてではなく
  スクリプト実行者として動くため、他の担当者のカレンダーは操作できません。そのため、
  期限切れによる自動解放・自動昇格が起きても、該当のカレンダーイベントは削除されません
  （期限が来て役目を終えたイベントがそのまま残るだけで、実害はありません）。同様に、
  Hold中の車両を受注確定した場合に削除できるのは受注確定を行った本人（＝1st Hold担当者）の
  イベントのみで、2nd Holdが同時に存在した場合はその担当者のイベントは削除されずに残ります。
- **カレンダー操作の失敗はHold登録・解除・受注確定を止めません**。イベントの作成・削除に
  失敗しても静かに無視し、本来の処理を優先します。

## 変更履歴（監査ログ）

Hold登録・2nd Hold登録・Hold解除（手動・自動）・受注確定のたびに、「変更履歴」シートへ
1行追記します（`AuditLogService.gs`）。列は 日時／操作／コミッション／モデル／担当者／
担当者メール／詳細です。誰が・いつ・何をしたかを後から追跡できるようにするための記録専用
シートで、更新・削除は行いません。アプリ側に専用の閲覧画面は設けていないため、確認は
スプレッドシートを直接開いて行います。時間主導トリガーによる自動処理（Hold期限切れの
自動解放・2nd Holdの自動昇格）は、担当者欄に「システム（自動処理）」と記録されます。

## Hold期限切れ処理の信頼性

Hold期限チェック（`processExpiredHolds`）は5分おきの時間主導トリガーから繰り返し
呼び出される冪等な処理のため、一時的なエラー（スプレッドシートAPIの瞬断等）が起きても
次回の実行が自動的に埋め合わせます。ただし、誰も気づけないまま失敗し続けると期限切れの
車両がいつまでも解放されない事態になり得るため、`triggerHoldExpiryCheck`
（`Triggers.gs`）は失敗時に2秒待って1回だけ即時リトライし、それでも失敗した場合は
設定タブの「システムエラー通知先」へメールで通知します（`notifySystemError_`）。
通知先が未設定の場合は通知をスキップします。

## 在庫データの整合性チェック

在庫の追加・編集はスプレッドシートへ直接行う運用のため、手作業ならではのミス
（コミッションの重複貼り付け、モデル名の記入漏れ、Holdステータス欄への想定外の値の
入力等）が紛れ込む可能性があります。アプリ起動時に一度だけ `api_checkInventoryIntegrity`
（`IntegrityService.gs`）を呼び出してチェックし、問題があれば画面上部にバナーで警告します。
「詳細を見る」で該当箇所の一覧を展開でき、閉じるボタンでその回のセッション中は非表示に
できます（データそのものを直しても再度開けば警告は消えます）。操作自体をブロックすることは
なく、あくまで早期発見のための警告です。

## システムマスタ（管理者限定）

設定タブは「テーマ」（表示設定、誰でも変更可）と「システムマスタ」（ロゴ・モデル写真・
メール通知設定・担当者、管理者のみ）の2系統に分かれています。システムマスタは
`Constants.gs` の `SYSTEM_ADMIN_EMAILS`（配列）に登録されたGoogleアカウントの
メールアドレスでログインしている場合のみ表示・変更でき、担当者マスタのように
スプレッドシートや画面から追加できる項目ではありません（コードを直接編集する
必要があります）。**管理者は複数人登録できます**（例:
`['admin1@example.com', 'admin2@example.com']`。`isSystemAdmin_` が配列内の
いずれかと完全一致するかで判定するため、人数の制限はありません）。

- **UIの非表示だけでなく、サーバー側でもデータを保護**しています。管理者判定
  （`isSystemAdmin_`）とそれに基づくリダクト（`redactSystemMasterSettings_`）・
  保存時のガード（`applySystemMasterGuard_`）は、`Api.gs`の`api_getSettings`/
  `api_saveSettings`だけでなく、呼び出される側の`SettingsService.gs`の
  `getSettings()`/`saveSettings()`自体の中で完結させています。Apps Scriptは
  トップレベル関数である以上、名前の末尾に`_`を付けてもクライアントの
  `google.script.run`から直接呼び出せてしまう（命名規則であって実行時の制限では
  ない）ため、権限チェックを`Api.gs`側だけに置くと、`google.script.run.getSettings()`
  のように生の関数を直接呼ばれた場合にリダクト・ガードが素通りしてしまいます。
  そのため関数自体に権限チェックを持たせ、どちらから呼ばれても安全にしています。
  管理者以外はテーマの変更のみ行えます。
  （未リダクトの生データが必要な内部処理――`api_getBootstrapData`の担当者メール
  突き合わせなど――は、専用の`getRawSettings_()`を使います。）
- **ロゴ・モデル写真は例外的に「値」自体は全利用者に届きます**。編集はシステムマスタに
  集約し管理者限定にしていますが、ロゴはトップバー、モデル写真はホーム画面のギャラリーとして
  全利用者の画面に表示する必要があるデータのため、`redactSystemMasterSettings_` では
  リダクト（空にする）対象から除外しています。管理者以外からの保存リクエストで
  変更を試みても、`applySystemMasterGuard_` が既存の保存値へ差し戻すため、表示専用の
  データとして安全に配れます。
- 管理者判定は `isSystemAdmin_(email)`（大文字小文字を区別しない完全一致）で行います。
- **`doGet`（`Code.gs`）のiframe埋め込み設定はALLOWALLにしています**。Googleサイトへの
  埋め込みで利用するための設定で、DEFAULT（同一オリジンのみ許可）にすると、Googleサイト
  側のページに埋め込んだ枠が別オリジンのiframe扱いになり読み込めず空白になってしまいます。
  ALLOWALLはGoogleサイト以外の任意のサイトからの埋め込みも許可してしまうため、
  クリックジャッキング（Hold登録・解除・受注確定ボタンを透明なiframe越しに誤クリック
  させる攻撃）の踏み台になり得ますが、Hold登録・解除・受注確定はいずれも
  `Session.getActiveUser()` でサーバー側から操作者本人のアカウントとして検証されるため
  （`Api.gs`・`HoldService.gs`・`OrderService.gs`参照）、悪用されても「操作者本人の
  アカウントとしての誤操作」に留まり、他人へのなりすましはできません。Googleサイトへの
  埋め込みが不要になった場合は、より安全なDEFAULTに戻すことを検討してください。

## 担当者マスタ

（設定タブの「システムマスタ」内にあります。上記の管理者制限を参照してください。）

設定タブから担当者を登録できます（最大30人、`STAFF_LIST_MAX`）。**名前・Googleアカウントの
メールアドレス・拠点名の組**で登録してください（`{ name, email, location }`）。メールアドレスが、
ログイン中のGoogleアカウントとの突き合わせに使われます（大文字小文字は区別しません）。
メールアドレスが重複する登録はできません。拠点名は未入力でも登録できます。

- **1st Holdと同じ担当者は、2nd Holdを登録できません**（`canRegisterSecondHold_`）。
  クライアント側でも送信前に確認しますが、最終判定はサーバー側で行います。
- **拠点名の自動反映**: Hold登録・2nd Hold登録・受注確定モーダルの
  「販売拠点」欄は、ログイン中の担当者が担当者マスタに登録している拠点名を初期値として
  自動的に入力します（`findStaffByEmail_` / `currentStaffLocation_`）。あくまで初期値のため、
  必要に応じてその場で編集できます。受注確定をHoldから続けて行う場合は、Hold登録時に
  入力・確定した販売拠点がそのまま引き継がれます（担当者マスタの拠点名を後から変更しても、
  過去のHold・受注の記録は変わりません）。
- **行の並び順はドラッグハンドル（⠿）で並び替えられます**（保存される配列の順序が
  そのまま並びになります）。並び順自体はアプリの動作には影響しません（担当者選択は
  常にメールアドレスの一致で行われるため）が、担当者選択のプルダウンや一覧表示の
  見やすさのために並び替えたい場合に使えます。

## メール通知設定

（設定タブの「システムマスタ」内にあります。上記の管理者制限を参照してください。）

Hold登録時・受注確定時・システムエラー発生時の通知先メールアドレスを、それぞれ
**担当者マスタ・モデル写真と同じ「1行1件のリスト形式」**で登録します
（`notifyHoldMailTo` / `notifyOrderMailTo` / `notifyErrorMailTo`、いずれも文字列の配列）。
以前は「,区切りの1つのテキスト欄」でしたが、「＋ 宛先を追加」で行を増やし、
不要な行は×ボタンで削除、ドラッグハンドル（⠿）で並び替えできる形式に統一しました
（並び順はメール送信の宛先（`to`）に反映される順序で、複数宛先へのCCのような一括送信の
ため実際の届き方には影響しません。担当者マスタ・モデル写真と見た目・操作感を揃えることが
主な目的です）。

- 1項目あたり最大20件（`NOTIFY_MAIL_LIST_MAX`）、メールアドレス1件あたり最大254文字
  （`NOTIFY_MAIL_MAX_LENGTH`）まで登録できます。空欄の行・大文字小文字違いも含めた
  重複行は保存時に除去されます（`normalizeMailList_`、担当者マスタの重複除去と同じ考え方）。
- **保存形式の移行**: 内部的には、以前の「,区切りの1文字列」から「順序を保った配列
  （JSON文字列として保存）」に変更しています（`getMailList_` / `normalizeMailList_`）。
  この変更より前に保存された「,区切りの1文字列」形式の値が残っていても、次回読み込み時に
  自動的にカンマ区切りとして分割して読み取るため、保存し直す必要はありません
  （モデル写真のGoogleドライブ共有リンク自動変換と同じ「読み出し時に自己修復する」考え方）。
- メール送信自体（`NotificationService.gs`）は、これらの配列をカンマ区切りの1文字列に
  結合したうえで `MailApp.sendEmail` の`to`にそのまま渡します（`MailApp`は元々カンマ区切りの
  複数宛先指定に対応しているため、送信ロジック自体への変更はありません）。

## Google Chat通知設定

（設定タブの「システムマスタ」内、メール通知設定と同じカード内にあります。）

Hold登録時・受注確定時に、メール通知とは別にGoogle Chatのスペースへも通知できます
（`notifyChatWebhookUrl`、1件のWebhook URL文字列）。

- **設定方法**: 通知したいGoogle Chatのスペースで「アプリと連携を追加」→「Webhookを管理」
  から受信Webhookを1件作成し、発行されたURL（`https://chat.googleapis.com/v1/spaces/...`）を
  設定タブの「Google Chat通知先（Webhook URL）」欄にそのまま貼り付けて保存してください。
- **メール通知先とは独立した設定**です。メール通知先が未設定でもWebhook URLだけ設定すれば
  Google Chatへの通知は動作しますし、逆にWebhook URLが未設定でもメール通知はこれまでどおり
  動作します（`NotificationService.gs`の`notifyHoldRegistered` / `notifyOrderConfirmed`が、
  メール送信・Google Chat送信をそれぞれ独立に「設定されていれば送る」判定にしています）。
- 通知内容はメール通知と同じ本文（コミッション・モデル・担当者・Hold期限や受注確定日時等）を
  そのままGoogle Chatのメッセージとして送ります（`sendChatNotification_`が
  `UrlFetchApp.fetch`でWebhook URLへJSON（`{"text": "..."}`）をPOSTします）。
- Webhook URLは`https://`から始まる文字列である必要があります（保存時に`validateChatWebhookUrl_`
  でチェックし、それ以外の値はエラーになります）。
- Google Chat側の障害やURLの設定ミスでメッセージが届かなかった場合でも、Hold登録・受注確定
  処理自体は失敗させません（`sendChatNotification_`が通信エラーを握りつぶし、ログにのみ残す
  設計のため）。

## ホーム画面（モデル別在庫リスト）

アプリを開くと最初に表示されるタブが「ホーム」です（アプリ名自体が「販売可能リスト」の
ため、ホーム画面に重ねて同じ見出しは表示していません）。設定タブから登録した**モデル単位**の
サムネイル写真・モデル名・現在の在庫台数を表示し、タイルをクリックするとそのモデル
（またはグレード群）で絞り込んだ在庫リストへ遷移します。在庫台数はHold中の車両も含めた
実数で、Hold登録・解除・受注確定のたびに更新されます。

- **PC（901px以上）は白背景のカードタイプUIの5列グリッド、タブレット・
  スマホ幅（900px以下）は横一列のリスト形式**: 画面の広いPCでは`.homeList`をCSS Gridの
  5列（20pxギャップ）にし、各タイル（`.homeRow`）を白背景・薄い境界線のカードにします。
  カードは「ヘッダー（モデル名＋グレード件数タグ）→写真→フッター（在庫台数＋矢印）」の
  3ブロック構成で、写真はカード内の白背景に収めて表示し、フッターは区切り線の下に
  在庫台数（アクセントカラー）と矢印（グレードのあるモデルは▸/▾、無いモデルは→）を
  並べる「詳細へ進めるリンク」の見せ方にしています（在庫リストの`.card__detailLink`・
  受注リストの`.orderCard__detailLink`と同じデザイン言語で統一。以前は写真をタイル
  全面に敷き、下部にグラデーションを重ねてモデル名・在庫台数を直接載せる
  「ショールーム」風の見せ方でしたが、カードタイプUIに刷新しました）。タブレット・
  スマホ幅では、毎日使う社内ツールとして「一目で在庫状況がわかる」情報密度を優先した、
  写真を小さめ（正方形のサムネイル）にした横一列のリスト形式のまま維持します
  （`@media (max-width: 900px)`でPC専用のカード表示を打ち消して元の見た目に戻す。
  現場の声を踏まえて選んだ元のレイアウトのため、狭い画面ではあえて変更していません。
  ヘッダー・写真・フッターの3要素はPC・タブレット/スマホ共通のDOM構造のままで、
  CSSの`order`だけで横一列に組み替えています）。書体はアプリ全体で引き続き
  細身・ジオメトリックなサンセリフ体（Barlow）のままです。

- **ボディタイプ（型）ごとのグループ表示・絞り込み**: 設定タブのモデル写真ごとに
  ボディタイプ（`Sedan` / `SUV` / `Station Wagon` / `Compact` / `Coupe` /
  `Cabriolet/Roadster` / `Mini Van`。`MODEL_BODY_TYPE_OPTIONS`、Constants.gs）を
  1つ選んで割り当てられます。
  1台でも割り当てられていれば、ホーム画面のモデル一覧はこの5種類の順序で
  グループ化され、各グループの先頭（そのタイプの最初のモデルタイルの直前）に
  型名の見出しを表示します（`groupModelPhotosByBodyType_`）。型を割り当てて
  いないモデルは「未設定」グループとして最後にまとめられます。1台も割り当てて
  いない場合はグループ化自体を行わず、この機能追加前と同じ見た目のまま
  表示されます（運用を始めたばかりの状態でも違和感が出ないように）。
  見出しの文字サイズ（19px）は、タイルに重ねて表示するモデル名（`.homeRow__model`、
  16px）より一段階大きくし、個々のモデルより上位の「見出し」であることが一目で
  わかるようにしています。見出しの上下の余白は、直前が型のクイックナビでも直前が別グループの
  モデルタイルでも常に同じ（24px）になるよう揃えており、先頭の見出しだけ
  クイックナビ側に寄って見えることがないようにしています。
  - **モデル一覧の上部には、型で絞り込むクイックナビ**（`#homeTypeNav`）を表示します。
    「すべて」と5種類のボディタイプが常にボタンとして並び、押すとその型だけに
    絞り込みます（`state.homeTypeFilter`）。該当モデルが1件も無い型を選んだ場合は
    その旨を案内します（`#homeTypeEmpty`）。
    - **上下スクロール中も常に押せるよう、トップバー・ツールバー（検索欄）と同じく
      `position: fixed`で画面上部に完全固定**しています（`syncFixedBars_`。
      直後に高さ実測済みのスペーサー`#homeTypeNavSpacer`を置き、後続のモデル
      一覧が隠れないようにする、`.toolbar` / `.toolbarSpacer`と同じ仕組み）。
    - **PCは折り返し無しの1行、タブレット・スマホ幅は横スクロール**にしています
      （`@media (max-width: 900px)`。5種類＋「すべて」を折り返し無しで並べると
      窮屈なため。折り返して縦に伸びると、固定表示の高さぶんスペーサーも
      伸びてしまい、その分モデル一覧が余計に下へ押し出されてしまうのを
      避ける狙いもあります）。
  - ボディタイプ自体は表示用の分類であり、在庫リストの検索・絞り込みには使いません
    （在庫データ側にボディタイプの列は無いため）。あくまでホーム画面でモデルを
    探しやすくするための情報です。

- **グレード別のタブ展開（自動判定）**: 在庫リストの「モデル」列には、実際には「A180」
  「A35」「A45」のようなグレード名のみが入力される運用（「Aクラス」のようなベース名は
  在庫データには存在しない）を前提に、設定タブのモデル写真ごとに「先頭の文字列」
  （`gradePrefix`）・「対象の文字列」（`gradeMarker`、任意）の2つだけを登録します。
  グレード名を一件ずつ手入力で列挙する必要はなく、在庫リストに実際にある型番のうち
  ①「先頭の文字列」で始まり、②「対象の文字列」が設定されていれば先頭部分を除いた
  残りにその文字列を含むものを、ホーム画面がその場で自動的に拾い集めます
  （`gradeCountsForEntry_` / `matchesGradeRule_` / `gradeRuleSpecificity_`、
  JavaScript.html）。1つの型番が複数の行の条件に一致しうる場合は、**より具体的な
  条件の行だけがその型番を拾い**、他の行には重複してカウントされません。具体性は
  「①対象の文字列を設定している行を優先」「②同じ条件同士（対象の文字列の有無が
  同じ同士）なら、先頭の文字列がより長い（＝より限定的な）行を優先」の順で決まります。
  例えば「CLA Coupe」（先頭の文字列「CLA」のみ）と「CLA Shooting Brake」
  （先頭の文字列「CLA」＋対象の文字列「T」）を登録すれば、在庫の「CLA18」「CLA22」は
  Coupe側へ、「CLA18T」「CLA22T」やその限定車「CLA18TZ」（Tを含むため）はShooting
  Brake側へ、設定を追加せずとも自動的に振り分けられます。また「Gクラス」（先頭の文字列
  「G」のみ）と「GLE」（先頭の文字列「GLE」のみ）を両方登録した場合も、「GLE350」は
  より長く具体的な「GLE」の方が優先されるため、「Gクラス」側には（同じく「G」から
  始まる）「G63」等、他のより具体的な行に横取りされなかった型番だけが残ります。
  **先頭文字が重なる兄弟モデル（G-Class・GLC・GLE・GLA・GLSなど）は、それぞれに
  専用の先頭の文字列を登録してください**。片方だけ（例えばGLEのみ）を登録して
  もう片方（例えばGLC）を登録し忘れると、GLCの型番は「G」で始まる他の行（Gクラス等）の
  受け皿に紛れ込んでしまいます。
  **在庫が実際に1台もない型番（グレード）は、この自動判定では
  検出できないため一覧に出てきません**（手入力で列挙していた以前のバージョンとは
  異なり、在庫データから動的に検出する方式のため）。
  グレードを検出したモデル行は、クリックすると即座に在庫リストへ遷移する
  のではなく、その場でグレードタブを展開します。PCの5列グリッドでは、展開中のタイルは
  グリッドの全列ぶんの幅（`grid-column: 1 / -1`）を使い、カード自体はそのまま（白背景・
  境界線）で、写真だけを大きく（アスペクト比16:9）表示します（`.homeRow.is-expanded`）。
  ヘッダー行の右側は、通常表示のグレード件数タグの代わりに「◂ 他のモデルを見る」の
  テキストリンクに切り替わり、押すと展開を解除して通常のグリッド表示に戻ります
  （`#homeGrid`のクリック委譲で、タイル自体のトグル処理がそのまま効きます）。
  フッターの矢印は▸（折りたたみ中）／▾（展開中）に切り替わり、在庫台数は展開中も
  そのまま表示し続けます。グレードタブ自体は、展開したタイルの直下に表示します。
  展開中のタイルは、内部に「他のモデルを見る」ボタンをネストできるよう`<button>`では
  なく`<div role="button" tabindex="0">`として描画し、キーボード操作（Enter/Spaceキー）
  による展開・折りたたみは`#homeGrid`への`keydown`委譲リスナーで別途維持しています。
  - **展開位置に関わらず、常に「クローズアップ表示→グレードタブ→他のモデル」の順で
    並びます**: 5列グリッド内でCSSの`order: -1`（PC専用。`@media (max-width: 900px)`側
    では`order: 0`に戻して打ち消す）を、展開中のタイルと、その直下に表示する
    グレードタブ（`.homeGradeTabs`）の**両方**に与えることで、配列・DOM上の並び順を
    変更せずに、クリックしたモデルが何番目にあってもクローズアップ表示とそのグレード
    タブが常にグリッドの先頭（＝画面上部）へ視覚的に移動し、他のモデルのタイルは
    その下にまとまって並びます（展開タイルにだけ`order:-1`を与えていた際は、
    グレードタブ側は既定の`order:0`のままだったため、先頭以外のモデルを展開すると
    グレードタブが他のモデルより下＝一番最後に表示されてしまう不具合があった）。
    JS側で配列を並べ替える方式は採らず、CSSのみで完結させることで、タブレット・
    スマホ幅の「その場でグレードタブを開くリスト形式」の並び順には影響しないように
    しています。
  - **タップして展開すると、その車両写真・グレードタブが一画面に収まる位置まで
    自動スクロールします**: モデル一覧が長く、タップしたタイルが画面外にある
    状態で展開しても、写真とグレードタブの両方が見える位置まで自動的にジャンプ
    します（`scrollIntoView({ behavior: 'smooth', block: 'start' })`）。トップバー・
    型クイックナビはどちらも`position: fixed`で画面上部に固定されているため、
    単純に展開したタイルの位置までスクロールするだけだとこれらの固定要素の
    下に隠れてしまいます。そのため、両方の固定要素の高さの合計をCSS変数
    （`--home-scroll-offset`。`syncFixedBars_`が実測して都度更新）として持ち、
    展開中のタイル（`.homeRow.is-expanded`）に`scroll-margin-top`として
    設定することで、スクロール後の位置が固定要素の下にちょうど収まるように
    しています。折りたたむ場合はスクロールしません（タップした位置のまま）。
  タブレット・スマホ幅（横一列のリスト形式）では、このクローズアップ表示は行わず、
  ベースモデル行の直下に写真幅ぶんインデントし、左に罫線を添えて表示することで
  「ベースモデル行から派生したタブである」ことが視覚的にわかるようにしています。
  グレードタブ自体をクリックすると、そのグレード1件だけに絞り込んだ在庫
  リストへ遷移します（自由入力のキーワード欄は使わず、専用の絞り込み状態として保持し、
  キーワードを手入力した時点で解除されます）。「先頭の文字列」を登録しないモデルは、
  従来通り行クリックでモデル名そのものを在庫リストのモデル列と直接照合し、即座に
  在庫リストへ遷移します（車種にグレードの区別が無い場合のフォールバック）。

- **モデル写真の登録順が、そのままホーム画面での表示順になります**。設定タブの
  モデル写真一覧で各行のドラッグハンドル（⠿）を掴んで並び替えると、保存後のホーム画面の
  タイル順にそのまま反映されます（`renderHomeGallery_`は配列の並び順どおりに描画するだけで、
  独自の並び替えロジックは持たないため）。担当者マスタ・メール通知先の並び替えとは異なり、
  こちらは実際の画面表示に直結する、実用上意味のある並び替えです。
- **写真は車両1台ごとではなく「モデル」単位**（例: Cクラス、3シリーズ）で管理します。
  個々の車両（コミッション）は在庫の入れ替わりが頻繁なため、車両ごとに写真を管理すると
  都度アップロード・削除の手間が発生します。モデル名という比較的変化の少ない単位で
  管理することで、運用の手間を抑えています。
- 設定タブの「システムマスタ」内「モデル写真（ホーム画面）」（管理者限定。詳細は
  「システムマスタ（管理者限定）」参照）から、モデル名・ボディタイプ（型）・写真URL・
  グレード自動判定条件（先頭の文字列・対象の文字列、ともに任意）の組を登録します
  （最大40件、`MODEL_PHOTOS_MAX`）。
  ボディタイプは`Sedan` / `SUV` / `Station Wagon` / `Compact` / `Coupe` /
  `Cabriolet/Roadster` / `Mini Van`から選ぶプルダウンで、任意入力です
  （未設定のままでも保存できます。ホーム画面での
  型ごとのグループ表示・絞り込みに使われます。「ホーム画面」の項を参照）。先頭の文字列・
  対象の文字列は1件あたり30文字まで（`MODEL_PHOTO_GRADE_RULE_MAX_LENGTH`）。
  ロゴ設定と異なり、モデル写真は複数枚をまとめて
  1つのScript Property（`MODEL_PHOTOS`）に保存するため、写真は**外部URL指定のみ**に
  対応しています（1件あたり1,500文字まで、`MODEL_PHOTO_URL_MAX_LENGTH`。署名付きURL等の
  長めの共有リンクにも対応できる余裕を持たせています）。data URLを直接貼り付けるような
  長すぎるURLは保存時にエラーになります（`normalizeModelPhotos_`）。また、1件あたりの
  上限内でも登録件数が多いと合計文字数がScript Propertiesの実際の保存上限（1プロパティ
  あたり9KB程度）を超えるおそれがあるため、JSON化した全体の文字数についても上限
  （`MODEL_PHOTOS_TOTAL_MAX_LENGTH`）を設けてチェックしています。
  画像はGoogleドライブの共有リンクなど、外部にアップロードしたうえでURLを指定して
  ください。
- モデル名・写真URLのどちらかが未入力の行は保存時に除去され、モデル名が重複する場合は
  先に登録した行が優先されます。
- モデル写真が1件も登録されていない場合は、ホーム画面に案内メッセージのみが表示されます
  （エラーにはなりません）。
- **写真URLはGoogleドライブの共有リンクをそのまま貼り付けるだけで反映されます**
  （`normalizeModelPhotoUrl_`）。ドライブの共有リンク（ファイルを右クリック→
  「リンクを取得」で得られる`https://drive.google.com/file/d/{ID}/view?usp=sharing`
  形式や`https://drive.google.com/open?id={ID}`形式のURL）は、そのまま`<img>`に
  指定してもHTMLビューアページが読み込まれるだけで画像としては表示されないため、
  ファイルIDを抜き出し、Googleの画像配信ドメイン（`lh3.googleusercontent.com`）の
  直接画像URLに自動変換して保存します。設定画面のプレビューにも保存前から同じ変換が
  反映されます（JavaScript.htmlに同名の関数をミラーしている）。ドライブの共有リンク
  以外のURL（他の画像ホスティングサービス等）はそのまま保存されます。以前に登録した
  未変換の共有リンクも、保存し直さなくても次回読み込み時に自動変換されます
  （`getModelPhotos_`）。
- **写真のサイズ・縦横比は管理者が気にする必要はありません**。ドライブの直接画像URLの
  末尾には`=w{MODEL_PHOTO_DISPLAY_WIDTH}`（既定1000px）を自動付与しており、Google側の
  サーバーがその幅にリサイズ済みの画像を返してくれるため、大きな元画像でも問題ありません。
  ホーム画面側の表示も`object-fit: cover`でタイルの枠に合わせて自動的にトリミングする
  ため、正方形以外の写真をそのまま登録しても崩れずに表示されます。

## 表示設定（テーマ）

設定タブの「テーマ」グループにある「表示設定」から、アプリ全体の配色を変更できます。
以前はテーマカラー・文字の色をそれぞれカラーピッカーで自由に指定できましたが、
組み合わせによっては文字が読みにくくなる（コントラスト比不足）懸念があったため、
あらかじめ視認性（WCAG AA基準：ボタン塗り用途で白文字とのコントラスト比4.5:1以上、
文字用途で背景とのコントラスト比4.6:1以上）を確認済みの**8種類の「着せ替え」プリセット**
（メルセデス・ベンツのカラーコード名にちなんだ、ブリリアントブルー・グラファイトグレー・
ヒヤシンスレッド・エメラルドグリーン・カラハリゴールド・アメジスト・カヴァンサイトブルー・
セレナイトグレー）から選ぶ方式にしています
（`Constants.gs` の `THEME_PRESETS`）。スウォッチをクリックするとその場でプレビューに
反映され、「保存」ボタンを押すと確定します。設定値はプリセットのキー（例: `steel`）
のみを `THEME_KEY` として保存し、実際の配色（`--primary` / `--primary-dark` /
`--primary-text`）はキーから導出します。テーマは管理者限定にしておらず、誰でも
変更できます。

**テーマはログイン中のGoogleアカウントごとに独立して保存されます**
（`PropertiesService.getUserProperties()`。ロゴ・メール通知先・担当者マスタ・
モデル写真のような全利用者共通の「システムマスタ」とは異なり、Script Properties
ではなくアカウント単位のUser Propertiesに保存する）。そのため、ある利用者が
テーマを変更・保存しても、他の利用者の画面には影響しません。各自が自分の画面だけ
好きな配色に変更できます（`getCurrentUserThemeKey_` / `setCurrentUserThemeKey_`、
`SettingsService.gs`）。

この機能はWebアプリのデプロイ設定が「実行するユーザー: アプリにアクセスするユーザー」に
なっていることが前提です（担当者のログイン連携と同じ条件。「セットアップ手順」参照）。
「自分」のまま・「全員（匿名可）」のままデプロイすると、全利用者が同じUser Properties
（デプロイしたアカウントのもの）を共有してしまい、実質的に全員共通のテーマに戻って
しまいます。

## ロゴ設定

設定タブの「システムマスタ」内「ロゴ」から、画面上部（トップバー）に表示するロゴ画像を
登録できます（管理者限定。詳細は「システムマスタ（管理者限定）」参照）。

- 画像ファイルをアップロードすると、ブラウザ上でdata URLへ変換され、そのまま設定項目
  （`LOGO_URL`）として保存されます。Script Propertiesは1項目あたり9KB程度が上限のため、
  なるべく小さい画像（数十KB程度まで）をお使いください。上限を超える場合は保存時にエラーに
  なります（`validateLogoUrl_`）。
- 大きな画像を使いたい場合は、外部（Googleドライブの共有リンク等、直接画像を指せるURL）に
  アップロードしたうえで、そのURLを「ロゴ画像URL」欄に直接指定してください。
- ロゴを未設定の場合は、従来通りテキストのブランド表示（「販売可能リスト」）のみが
  表示されます。

## 在庫リストの表示・検索

- **カードの高さは常に一定**: 在庫あり・Hold中・2nd Hold中のどの状態でも、カード自体の
  高さは変化しません。Hold情報の表示エリア（`.card__holdArea`）は高さ150px固定・内部
  スクロール形式（Hold未登録の車両には「現在Hold登録なし」というプレースホルダーを表示）に
  加えて、カード上部（モデル・コミッション・比較ピンの行＋バッジの行、`vehicleTopHtml_`）を
  常に2行固定にしています。以前はモデル・コミッション・バッジ・比較ピンを1つの折り返し
  コンテナに詰めていたため、バッジの個数（2個／3個）やモデル名・コミッションの文字数の
  組み合わせによって折り返し方が変わり、在庫あり／Hold中／Hold中（2nd有）でカードの
  高さが揃わないことがありました。
  - **2nd Holdは1st Hold（左）・2nd Hold（右）の横並び表示**（`.card__holdArea--split`。
    在庫リスト・マイページのカード、車両詳細モーダルで共通）。150pxという固定高さは、
    この横並び表示に2nd Holdの内容（担当者・残り時間・解除ボタン）まで収まる高さを基準に
    決めている（縦積みだと2nd Hold分の高さが必要になり、カードの高さを統一できなかった）。
- **グループ表示は廃止**: 以前あった「グループ表示」プルダウンは廃止し、常にフラットな
  カード一覧で表示します。
- **可能月ごとの在庫確認**: 「可能月」プルダウンで、実際に在庫が持つ可能月（＋当月は在庫が
  なくても常に選択肢に表示）から選んで絞り込めます。可能月と連動しており、月を選ぶと
  その月に登録可能な車両だけに絞り込めます。あわせてツールバーに絞り込み後の合計台数
  （「該当◯台」）を表示します。
- モデル・コミッションでの自由検索、「Hold済みを含む」チェックボックスと組み合わせて
  絞り込めます（`searchInventory`）。
- **ホームに戻ると検索条件は自動でリセットされる**: 在庫リストで検索・絞り込みをした
  あとにホームタブへ移動すると、検索キーワード・可能月・グレード絞り込みがすべてリセット
  され、次に在庫リストを開いたときは全在庫表示の状態に戻ります（`resetInventoryFilters_`、
  `switchToTab_`。メインタブのクリック・「戻る」ボタン・ホームのモデルクリックなど、
  ホームへ遷移するすべての経路で自動的に働きます）。検索条件を絞り込んだままだったことを
  忘れて混乱するのを防ぐためです。
- **タブ切替時は常にページ先頭までスクロールする**: 全タブは同じ1つのdocument上で
  `display: none`/`block`を切り替えているだけのため、スクロール位置はタブをまたいで
  共有されてしまう（例: ホームでスクロールした状態でモデルをクリックすると、在庫リストも
  同じスクロール位置のまま表示され、ツールバー等が見えない状態で開いてしまう）。
  `switchToTab_`の中で毎回`window.scrollTo(0, 0)`を呼び、タブ切替のたびに常に
  ページの一番上から表示されるようにしている。
- **カードグリッドは4列（PC幅）、受注リストは3列**: 幅の広いPC画面では、在庫リストは
  1行に4枚、受注リストは1行に3枚カードが並びます。ノートPC幅（1400px以下）では在庫リストが
  窮屈にならないよう3列に落とし、タブレット幅（900px以下）・スマホ幅（600px以下）では
  さらに列数が落ちます（`Stylesheet.html`）。
- **「詳細を見る」は画面中央のポップアップで確認（カード自体は伸びない）**: 車両スペック
  （ステア・有償OP・入港予定日・可能月・VPC）とHoldの詳細（リード番号・登録月・下取車・
  OSS・保険・支払方法）は、カード内には表示せず「▸ 詳細を見る」タップで画面中央のモーダル
  （`#inventoryDetailModal`・`vehicleDetailHtml_`）にまとめて表示します。以前はカード内の
  折りたたみ（`<details>`）で、開閉のたびにカード自体が伸び縮みして他のカードとサイズが
  揃わなくなっていました。受注リストの「詳細を見る」（`#orderDetailModal`・
  `orderDetailHtml_`）も同じパターンです。カード上の一次情報（モデル・コミッション・
  ステータスのバッジ、MP・カラー）は引き続き常に表示され、隠れるのはこの2種類の詳細だけです。
- **詳細モーダル表示中は背景がスクロールしない**: モーダルを開いている間は`body`の
  スクロールをロックし（`openModal` / `closeModal`が`body.modal-open`をトグル）、
  背景の在庫リスト・受注リストが一緒に動いてしまわないようにしています。またモーダル
  自体も、ヘッダー・フッター（`.modal__header` / `.modal__footer` / `.modal__stepBar`）
  は固定し、`.modal__body`だけがスクロールする構成にしています。本文内のモデル名・
  ステータスバッジ（`vehicleTopHtml_`が出力する`.card__top`、受注リストの
  `.orderCard__top`）は固定せず、車両スペック・Hold詳細などの残りの情報と一緒に
  通常通りスクロールします（固定されるのはモーダル自体の見出し・閉じるボタンのみ）。
- **1st Hold・2nd Holdの両方が埋まっている車両は色を変える**: 「Hold解除」の項を参照。
- **表示形式（カード／表）はアイコンのみで切替**: 在庫リスト・受注リストとも、ツールバーの
  切替ボタンはアイコンのみで、文字ラベルは表示しません（マークのみで判断できるため）。
  ホバー時のツールチップ・スクリーンリーダー向けの`aria-label`は残しています。
- **表示形式「表」もカードタイプ**: 「表」は素のHTML `<table>` ではなく、1台=横1行の
  “行カード”（`.rowCard`）として表示され、角丸・影・ホバーで浮き上がる見た目はカード表示と
  統一しつつ、多台数を一覧で見比べられる密度を両立しています。操作ボタンの列は固定幅にして
  あり、在庫あり（ボタン2つ）・Hold中（ボタン2つ）・2nd Hold登録済み（ボタン1つ）のどの
  行でも、先頭ボタンの位置・他の列の位置が揃うようにしています（以前はボタン数で列幅が
  変わり、行ごとに列がずれる不具合があった）。
  - **不具合修正（状態バッジと操作ボタンの重なり）**: 状態列の幅が「Hold中」「在庫あり」
    という短い文言を前提にした狭さ（108px）のままだったため、2nd Holdまで埋まっている
    車両の「Hold中（2nd有）」というより長い文言がはみ出し、隣の操作ボタン列と重なって
    表示されてしまっていた。状態列を150pxへ広げ、重ならないようにした。
  - **行（カード）をタップすると車両情報を画面中央にカード表示**: 「表」は横スクロールで
    多くの項目を並べるため、画面幅によっては有償OP等の車両情報や右側の状態列がスクロール
    しないと見えない。そこで、行（チェックボックス・操作ボタン以外の部分）をタップすると、
    既存のカード表示（`.card`、`vehicleCardHtml`）と同じ見た目・同じ情報量で、その車両の
    詳細を画面中央のモーダルに表示するようにした（`openInventoryDetailModal_`、
    `#inventoryDetailModal`）。モーダル内のHold・受注・2nd Hold・Hold解除ボタンも
    そのまま操作でき、押すとモーダルを閉じたうえで通常のHold登録・受注確定モーダルへ
    進む。状態は在庫状況の色つき左罫線（`.rowCard--available`等）と右側のバッジで
    分かるため、左端の状態ドットは廃止した（現場からの指摘で判明。以前は比較用
    チェックボックスの下に常時表示していた）。横スクロール自体はそのまま残しており、
    あくまで「スクロールしなくても車両情報を確認できる」導線を追加したもの。
  - **不具合修正（表示形式「表」にHold解除の導線が無かった）**: 表形式にはHold解除の
    ボタンが用意されておらず、カード表示に切り替えない限りHoldを解除できなかった。
    状態バッジの下に「1ST HOLD解除」「2ND HOLD解除」ボタンを追加し、カード表示と同じ
    Hold解除モーダルを開けるようにした。
  - **比較用チェックボックスをモデル名の先頭行へ移動**: 以前は左端の専用列（状態ドットと
    並ぶ「ピン列」）に置いていたが、モデル名の上（1行目）に移動し、続く2行目・3行目に
    モデル名・コミッションを表示するようにした（現場からの指摘で判明。モデル名と
    コミッションの間に挟んで3行にする案は不採用）。カード表示側の比較ピン
    （`.card__comparePin`）と同じ「チェックボックス＋『比較』文字」の見た目にしている。
  - **車両情報の列は中央揃え・高さも均一化・列間の余白は行全体で均一**: MP・ステア・
    カラー・有償OP・入港予定日・可能月・VPCは、モデル名・コミッションの識別列や状態・
    操作ボタンの列とは区別して、ラベル・値ともに中央揃えにした。また、MP・VPCの値
    （英数字）とステア・カラー等の値（日本語）を同じスタイルで混在表示すると、フォントの
    フォールバック先の違いにより行の高さがブラウザの自動計算でわずかにずれ、値の上下位置が
    項目によって揃わなくなっていたため、`line-height`を明示的に固定して解消した（現場からの
    指摘で判明）。モデル列は以前210px幅にしていたが、実際のコンテンツ（比較チェックボックス・
    モデル名・コミッション）は最大でも70px程度しか使っておらず、左詰めの文字の右側に
    無駄な余白が生まれ、モデル→MPの間だけ他の列間より大きく間延びして見えていたため
    （現場からの指摘で判明。一時的に左右へ`1fr`の空列を挟んで車両情報ブロックを中央寄りに
    見せる案も試したが、モデル→MP間の余白がかえって目立つ結果になったため不採用）、
    モデル列を実コンテンツ幅に合わせて100pxまで縮め、列同士はすべて同じgap（16px）だけで
    隣り合うようにし、行全体で余白が均一に見えるようにした。
  - **不具合修正（状態・操作ボタンがカードの枠からはみ出す／カードが画面幅いっぱいに
    間延びする）**: 列を固定幅にすると、`.rowCard`は`.rowCardList`
    （`display:flex; flex-direction:column;`）の子要素として横幅が親にstretchされるため、
    明示的な`min-width`が無いと、グリッドの列（特に最後の状態・操作ボタン列）がカード
    自身の枠（border/background）の外側へはみ出して表示されてしまっていた（現場からの
    指摘で判明）。`.rowCard`・`.rowCardList`双方に列の合計幅と同じ`min-width`（在庫リスト
    1348px、受注リスト928px）を指定し、枠が必ず内容を包み込むようにした。あわせて
    `.rowCardList`に`width: fit-content`を指定し、列がすべて固定幅になった今、カード自体が
    画面幅いっぱいに伸びて最後の列の右側だけ余白が空いてしまう状態も解消した（画面幅が
    列の合計幅より狭い場合は、従来通り`.tableScroll`の横スクロールで対応する）。受注リストの
    顧客名の列も同様の理由で210px→110pxに縮め、`.rowCard--order`/`.rowCardList--order`で
    それぞれ上書きしている。
  - **状態列（Hold解除ボタン）の高さ固定**: Hold中はHold解除ボタンが1つ、Hold中
    （2nd有）は2つに増えて状態列が縦に伸びる分だけ、行（カード）自体の高さが
    在庫あり・Hold中・Hold中（2nd有）でバラバラになっていたため、状態列の高さを
    常に一定にして吸収するようにした（`.card__holdArea`と同じ考え方）。あわせて
    Hold解除ボタンは「Hold中」バッジの真下・中央に来るよう中央揃えにしている。
- **受注リストにも同じ表示形式切替を実装**: 受注リストのツールバーにも「カード／表」の
  切替を追加しました。「表」では顧客・コミッション・モデル・MP・VPC・有償OP・担当者・
  リード番号・登録月・下取車の有無・OSS登録の可否・保険加入の有無・支払方法・
  受注確定日時・販売拠点を1件=横1行の行カードで表示します（比較機能・操作ボタンは
  受注リストには無いため、在庫リストとは別の列構成です）。当初はMP・VPC・有償OP・
  下取車の有無・OSS登録の可否・保険加入の有無・支払方法が表示されておらず、詳細
  モーダル（`orderDetailGridHtml_`）を開かないと確認できなかったため（現場からの
  指摘で判明）、これらも列として追加した（`下取車`/`OSS`/`保険`は行では省スペースの
  ため短縮表記にしているが、値自体は詳細モーダルと同じ）。
  - **不具合修正（顧客〜モデル・モデル〜担当者の間に不要な余白）**: 顧客・モデルの列を
    `fr`（可変幅）にしていたうえ、行カードの共通スタイル（`.rowCard`／`.rowCardList`）の
    min-width（在庫リスト向けに1490pxを指定）をそのまま受け継いでいたため、列数の
    少ない受注リストの行では余った横幅を可変幅の2列だけが吸収し、顧客名〜モデル・
    モデル〜担当者の間に大きな余白が空いてしまっていた（現場からの指摘で判明）。
    在庫リストと同様にすべての列を固定幅にし、min-widthも受注リスト自身の列合計
    （`.rowCard--order`/`.rowCardList--order`）に上書きすることで、余白をなくし
    スクロールの手間を減らした（顧客名の列はその後さらに110pxへ縮めている。詳細は
    「在庫リストの表示・検索」内の該当項目を参照）。

## 受注リストの月別管理・検索

受注リストは、以下を組み合わせて必要なデータを素早く絞り込めます。

- **月ごとのグループ表示**: グループ表示で「月ごと」を選ぶと、受注確定日時（`orderedAt`）を
  基準に月ごとにグループ化されます（`api_listOrders` が `orderedMonth`＝`2026-08` 形式の値を
  付与）。各グループの見出しには「◯台」の件数を表示し、月ごとのトータル台数がひと目で
  把握できます。グループ表示なしの場合も、画面上部に絞り込み後の合計台数（「該当◯台」）を
  常に表示します。
- **拠点ごとの検索**: 「拠点で絞り込み」は「岐阜」「大垣」「多治見」「高山」から選択する
  プルダウンです（自由入力ではなく選択式。`html/Index.html` の固定選択肢）。
- **担当者ごとの検索**: 担当者マスタから選択する専用のプルダウンで、完全一致の絞り込みができます。
- **自由検索**: モデル・コミッション・顧客名・担当者・販売拠点を横断したキーワード検索です。
  上記の拠点・担当者フィルタと組み合わせて（AND条件で）絞り込めます（`searchOrders`）。
- **カード表示は顧客名が主役**: 受注リストのカードは「誰が買ったか」がひと目でわかるよう、
  顧客名を大きな見出しにし、その下に担当者名・リード番号を表示します。モデル・コミッション
  などその他の情報はカード下部の詳細情報エリアに表示します（`orderCardHtml`）。

## マイページ

タブ「マイページ」は、ログイン中のGoogleアカウント（担当者メールアドレス）に紐づく
**自分がHold中の車両**と**自分が受注した車両**だけを抜き出して表示します。在庫リスト・
受注リストは全担当者ぶんの案件が並ぶため、「自分の案件だけを今すぐ確認したい」場面向けの
専用ビューです。

- **絞り込みはメールアドレスで行う**（`emailsMatch_`。表示名ではない）: 担当者マスタの
  表示名は後から変更され得るため、名前同士の比較だと表示名を変えただけで自分自身の
  Hold・受注が見つからなくなる不具合の原因になります。Hold解除・受注確定の権限判定
  （`canCancelHold_` / `canConfirmOrder_`）と同じ考え方で、Hold中の車両は
  `holdStaffEmail` / `secondHoldStaffEmail`、受注した車両は`staffEmail`が、ログイン中の
  メールアドレスと一致するものだけを表示します。
- **担当者マスタに未登録のGoogleアカウントの場合は案内メッセージのみ表示**します
  （`renderMyPageNoStaffState_`）。担当者を特定できず、そもそもHold・受注の担当者メール
  とも突き合わせようがないためです。
- **カードは在庫リスト・受注リストと同じもの（`vehicleCardHtml` / `orderCardHtml`）を
  そのまま再利用**しています。専用の簡易カードを新設するのではなく既存のカードを流用する
  ことで、比較ピン・Hold解除・受注確定・詳細を見る等の操作がマイページ上でも在庫リスト・
  受注リストと完全に同じ挙動になります（見た目・操作感の統一、実装の二重管理を避ける
  両方の狙い）。
  - この再利用に伴い、カード上のボタン操作（`openActionModal` / `openCancelHoldModal` /
    `toggleCompare_` / `openInventoryDetailModal_` / `findOrderByCommission_`）の車両・
    受注の参照先を、在庫リスト・受注リストの検索・絞り込み条件に左右される
    `state.inventoryItems` / `state.ordersGroups` だけでなく、フィルタに左右されない
    全件キャッシュ（`state.allInventoryItems` / `state.allOrders`）にもフォールバックする
    よう修正しています。これが無いと、例えば在庫リストで絞り込み中にマイページを開いた
    場合、絞り込みで対象外になっている自分のHold車両のボタンを押しても何も起きない
    （または受注確定モーダルの内容が正しくプリフィルされない）不具合になります。
- 表示専用データの取得は、ホーム画面の在庫サマリーと同じ考え方で、既存の全件取得
  （`state.allInventoryItems`）を再利用しつつ、受注については新たに`loadMyPageOrders_`
  （フィルタ無しの`api_listOrders`呼び出し）を追加しています。

## リード番号の入力形式

Hold登録・2nd Hold登録・受注確定の各モーダルの「リード番号」欄は、「L-」固定の接頭辞＋
数字のみで入力する専用UIになっています（数字以外を入力しても自動的に除去されます）。
スプレッドシートには `L-11111111` のように、常に「L-」付きの文字列として保存されます
（`normalizeLeadNumber_`。サーバー側でも必ず正規化・検証するため、万一クライアント側の
チェックをすり抜けた入力があっても不正な形式では保存されません）。入力欄自体には
サンプル値は表示されません（空欄から数字を入力します）。

## 登録月の初期値

Hold登録・2nd Hold登録・新規の受注確定（Holdを経由しない「受注」ボタン）は、
いずれもモーダルを開いた時点の「今月」が登録月欄の初期値になります（編集可）。
**Holdからの受注確定**（「受注確定」ボタン）についても同様で、Hold登録時点の月ではなく、
受注確定を行う「今月」が初期値になります（Hold登録からしばらく経ってから受注確定される
ケースがあるため、Hold時点の月を引き継ぎません）。

## スマートフォンでの入力時の自動ズーム防止

`.input`（テキスト入力・セレクトボックス共通のクラス）のフォントサイズは16px以上に
しています。iOS Safari等のモバイルブラウザは、フォーカスした入力欄のフォントサイズが
16px未満だと、ユーザーが読みやすいように画面全体を自動的に拡大表示する仕様があり、
Hold登録・受注確定モーダルに限らずすべての`.input`（検索欄・設定画面の各種入力欄を
含む）でこれが起きると、入力のたびに画面が拡大・縮小されて操作しづらくなります。
16px以上にすることでこの自動ズームが発生しなくなり、画面が固定されたまま入力できます。

## 受注確定時の紙吹雪演出

Hold登録・2nd Hold登録では何も表示しません。受注確定が成功すると、
文字・カードなどのポップアップは一切出さず、画面いっぱいに盛大な紙吹雪だけを3波に分けて
降らせ、開始の瞬間に画面中央を一瞬光らせます（CSSアニメーションのみで実装。外部ライブラリ
不要。`triggerConfetti_`）。

## PWA対応（ホーム画面への追加）

`PwaService.gs` で、ウェブアプリのURL（`.../exec`）に直接アクセスした場合に、
スマートフォンの「ホーム画面に追加」からアプリのように（ブラウザのアドレスバー等を
表示しない状態で）起動できるようにしています。

- Google Apps Scriptのウェブアプリは、通常のWebサーバーのようなパスベースの
  ルーティングができず、`doGet(e)` のクエリパラメータでしか振り分けられないため、
  マニフェスト（`?resource=manifest`）・Service Worker（`?resource=sw`）は
  `doGet(e)` の入口（`Code.gs`）で振り分けて配信している。
- アイコンを別ファイルとして配信する手段が無いため、車のシルエットのアイコンを
  Playwrightでラスタライズし、PNGをBase64のdata URIとしてマニフェスト・
  `apple-touch-icon` に直接埋め込んでいる（`PWA_ICON_192_BASE64` /
  `PWA_ICON_512_BASE64`。差し替える場合はこの2定数を新しい画像のBase64文字列に
  置き換えるだけでよい）。
- Service Workerはオフラインキャッシュを一切行わない（在庫・Hold・受注データは
  常に最新をスプレッドシートから取得する必要があるため）。インストール条件を
  満たすための最小限のfetchハンドラのみを配信している。
- **注意**: このアプリをGoogleサイトへの埋め込みで使う場合、ブラウザが実際に開いている
  トップレベルのページはGoogleサイト側のページであり、このアプリのマニフェスト・
  Service Workerはあくまで埋め込みiframe内でのみ有効なため、「ホーム画面に追加」
  （PWAとしてのインストール）はGoogleサイト側のページに対しては機能しない。
  ウェブアプリのURLに直接アクセスした場合にのみ、ホーム画面への追加・スタンドアロン
  起動が期待通り機能する。実際にデプロイしたウェブアプリのURLで、スマートフォンの
  ブラウザから動作確認することを推奨する。

## アイコン・設定画面のデザイン

- **トップバーのレイアウト**: 左ブロック（`.topbar__left`）に「戻る」「更新」ボタン、
  右ブロック（`.topbar__user`）にログイン中のユーザー情報（担当者名・メールアドレス）を
  配置し、中央にアプリ名「販売可能リスト」＋ロゴ（設定されている場合のみ、`.topbar__brand`）
  を表示しています。中央のブランド表記は、左右のブロックの幅に関わらず常に画面中央に
  来る必要があるため、`.topbar__brandRow` を `position: relative` にし、`.topbar__brand`
  を `position: absolute; left: 50%; transform: translate(-50%, -50%)` で中央配置する
  方式にしています（左右のブロックを同幅の`1fr`トラックに揃えて中央寄せする方式だと、
  左右どちらかの内容量が変わるたびに調整が必要になるため、中央配置専用の要素を独立して
  絶対配置する方式のほうが崩れにくい）。テキストサイズ（`.topbar__brandText`）はロゴの
  高さに近いスケールに揃えており、干渉しないようにしています（PCビュー・タブレット/
  スマホビューそれぞれの`.topbar__logo`の高さに応じて調整。PCビューのみ拡大する
  ブレークポイント内でも同様に拡大）。ホーム・在庫リスト・受注リスト・設定のタブは、ブランド行の下に
  独立した行として中央寄せで配置しています。
  - **PC（901px以上）は左サイドバー、タブレット・スマホ幅（900px以下）は従来どおり
    上記のトップバー方式**: PCビューでは、ロゴ・アプリ名・ナビ（ホーム／在庫リスト／
    受注リスト／Gクラス予約リスト／マイページ／設定）・ログイン中のユーザー情報を
    画面左側に固定した縦のサイドバー（`.sidebar`、幅232px）にまとめ、トップバー側は
    ページ見出し（「販売可能リスト」）と「戻る」「更新」ボタンだけが残るスリムな
    ヘッダーになります。サイドバー方式はタブレット・スマホ幅では画面が狭すぎて
    畳む必要が生じ、既存の実務向けレイアウトを壊してしまうため、PCビューのみに
    限定しています（`@media (min-width: 901px)`）。サイドバーのナビ項目は、
    トップバーの水平タブ（`#mainTabs`）と同じ`.tabs__item`クラス・`data-tab`属性を
    共有して描画しているため（Index.html）、`switchToTab_`（JavaScript.html）の
    `document.querySelectorAll('.tabs__item')`によるis-active状態の一括トグルが
    そのまま両方に効き、別途同期用のコードを書く必要がありません。ロゴ・ユーザー
    情報も`applyLogo` / `renderTopbarUser`が両方の要素（`#topbarLogo` /
    `#sidebarLogo`、`#topbarUser` / `#sidebarUserInfo`）へ同じ内容を反映します。
- **「戻る」「更新」ボタン**: トップバー左側（`.topbar__left`）に配置しています。
  「戻る」（`#btnNavBack`）はタブ切替のたびに記録される画面履歴（`state.navHistory`、
  タブ名のスタック）を1つ戻ります。ホームのモデル・グレードクリックによる在庫リストへの
  遷移も含め、`switchToTab_` を経由するすべての画面遷移で自動的に記録されるため、
  個々の遷移元で履歴を意識してコーディングする必要はありません。履歴が空の場合は
  ボタンを無効化します。「更新」（`#btnRefresh`）は、起動時と同じ処理（`reloadAll_`。
  設定・担当者判定・整合性チェック・在庫/受注/ホームの一覧を再取得）をその場で再実行し、
  他の利用者による変更をページ全体を再読み込みせずに反映します。見た目は「戻る」と
  まったく同じアウトラインの円形ボタンで統一しており（`.topbar__navBtn`）、読み込み中
  だけアイコンが回転してフィードバックします（`.topbar__navBtn--refresh.is-spinning`。
  `prefers-reduced-motion: reduce`環境ではアニメーションを無効化）。
  - **スマートフォン幅（600px以下）でのユーザー情報の非表示**: 担当者名・メール
    アドレスは長さ次第で折り返し等により崩れやすいため、スマホ幅では`.topbar__user`
    を`display: none`にして非表示にしています。中央のブランド表記は独立して絶対配置
    されているため、ユーザー情報の表示可否からは影響を受けません。
- **アイコン**: 設定タブの各項目見出しなどに使う絵文字アイコンは、
  Google／Teslaのアプリのようなミニマルな線画アイコン（インラインSVG）に置き換えています。
  `html/Index.html` の先頭にアイコン一式を `<symbol>` として定義しており（外部アイコン
  ライブラリ・フォント不要）、使う側は `<svg class="icon"><use href="#icon-xxx"></use></svg>`
  で参照するだけです。
- **設定画面のカードデザイン**: 以前は1つの大きなカードの中に全設定項目を並べていましたが、
  項目ごとに独立したカード（島）に分け、1列で縦に並べるレイアウトに変更しました
  （`.settingsGrid` / `.settingsCard`）。2列グリッドや段組み（masonry）レイアウトも
  試しましたが、カードの高さがまちまちだと「同じ行のカードの高さが最も高いカードに
  揃ってしまい下に不揃いな余白ができる」「段組みの列の合計高さがずれて次のカードとの
  間隔だけ広がる」といった、カード同士の隙間が不揃いに見える問題がどうしても残るため、
  確実に隙間が一定になる1列の縦積みに統一しています（Google／Teslaの設定画面も
  同様に1列でカードを並べるスタイルです）。

## スプレッドシートの自動セットアップ（SetupService）

元データスプレッドシート（xlsx）を手作業でアップロード・貼り付けなくても、任意の空の
Googleスプレッドシートに本プロジェクトをコンテナバインドした状態で、GASエディタから
`setupSpreadsheet_()` を一度実行するだけで、在庫リスト・Holdリスト・受注リスト・
Gクラス予約リスト・変更履歴の5タブ・ヘッダー・入力規則（選択式の列のドロップダウン）・
列見出しの説明メモ・コミッション列の書式（先頭0保持）・Hold期限チェックの時間主導
トリガーまで一括で整えられます。既存のシートがある場合は作り直さず、そのまま利用します。

- **各タブの列は、Constants.gsの列定義（`INVENTORY_COLUMNS` / `HOLD_COLUMNS` /
  `ORDER_COLUMNS` / `GCLASS_COLUMNS` / `AUDIT_LOG_COLUMNS`）から自動生成**されます
  （`getOrCreateSheet_`）。
  そのため、今後アプリ側に列が追加された場合も、この自動セットアップのコード自体を
  変更する必要はありません。
- **選択式（`type: 'select'`）の列には、その選択肢のみを許可する入力規則（ドロップダウン）を
  自動設定**します（`applySelectValidations_`。例: Holdステータス／ステア／在庫開示／
  下取車の有無／OSS登録の可否／保険加入の有無／支払方法／順番）。想定外の値（表記ゆれ・
  入力ミス）が直接編集で紛れ込むのを未然に防ぎます（在庫データの整合性チェックが検出する
  「不明なHoldステータス」等の不整合は、そもそもこの入力規則で防げます）。この入力規則は
  スプレッドシートのUIから手入力する場合にのみ働き、アプリ自体の書き込み（`setValues()`）
  には影響しません。
- **列見出しには、入力形式や注意点を説明するメモ（セルコメント）を自動設定**します
  （`applyHeaderNotes_`）。リード番号・登録月・可能月の入力形式、コミッション列の書式を
  変更してはいけない理由、担当者メール・開始日時・期限・カレンダーイベントID・受注確定
  日時といったアプリが自動設定する列を手動編集しないでほしい旨などを記載しています。
  コードを読まなくても、スプレッドシートを直接開いた運用担当者がその場で確認できます。

コンテナバインドのスプレッドシートを開くと、メニュー「販売可能リスト」からも
「初期セットアップ（5タブを作成）」「入力規則・列見出しの説明メモを再設定」
「コミッション列を書式なしテキストに再設定」を実行できます（`onOpen`）。
「入力規則・列見出しの説明メモを再設定」（`applySelectValidationsAndNotes_`）は、
入力規則・説明メモの機能が追加される前に`setupSpreadsheet_()`を実行済みだった
既存のスプレッドシートに、これらを後から反映したい場合に使います（既存のシート・
データはそのまま変更しません）。

## 元データスプレッドシート

`vehicle-order-app-master-data.xlsx`（チャットで送付済み）に、上記の列構成に合わせた
「在庫リスト」「Holdリスト」「受注リスト」「使い方」の4タブを用意しています（Gクラス
予約リストはこのxlsxには含まれていません。後述のSetupServiceで自動生成してください）。
既存データはこのファイルの「在庫リスト」タブ・薄い青色のヘッダー列（モデル〜在庫開示）へ
貼り付けてください。「Holdリスト」「受注リスト」タブはアプリが自動的に読み書きするため、
手入力は不要です。スプレッドシートを新規に用意する場合は、上記の SetupService
（`setupSpreadsheet_()`）を使えばこのファイルなしでも「在庫リスト」「Holdリスト」
「受注リスト」「Gクラス予約リスト」（＋変更履歴）のタブを自動生成できます。このxlsxは、
既存データを一括で貼り付けたい場合や列構成の参考にする場合にご利用ください。

**既存の在庫リストに「車種」列がある場合の移行について**: 今回、在庫リスト・受注リストの
列構成から「車種」列を廃止しました。アプリはスプレッドシートの列を「見出し文字列」ではなく
「並び順（列の位置）」で読み書きするため、既存の在庫リストに「車種」列がまだ残っている状態で
このバージョンのコードを使うと、以降の列がすべて1列分ズレて読み込まれてしまいます。
移行時は次のいずれかの対応をしてください。
- 既存の「在庫リスト」シートから「車種」列（通常はA列）を削除する。
- または、新しい空のスプレッドシートに `setupSpreadsheet_()` で5タブを作り直し、
  「車種」列を除いたうえで既存データを貼り直す。

## セットアップ手順

1. **スプレッドシートの準備**（どちらかを選択）
   - **方法A（推奨・最速）**: 空のGoogleスプレッドシートを新規作成し、下記2でこのプロジェクトを
     コンテナバインドしたあと、GASエディタから `setupSpreadsheet_()` を一度実行するだけで
     「在庫リスト」「Holdリスト」「受注リスト」「Gクラス予約リスト」「変更履歴」の5タブ・
     ヘッダー・入力規則・コミッション列の書式・Hold期限チェックのトリガーまで自動で整います
     （詳細は「スプレッドシートの自動セットアップ（SetupService）」の項を参照）。既存データが
     ある場合は、後から「在庫リスト」タブに貼り付けてください。
   - **方法B（既存データを一括で貼り付けたい場合）**: `vehicle-order-app-master-data.xlsx`
     （チャットで送付済み）をGoogleドライブにアップロードし、Googleスプレッドシートとして
     開きます（アップロード時に自動変換されない場合は「アプリで開く」→
     「Googleスプレッドシート」）。既存データは「在庫リスト」タブに貼り付けてください。
     すでにお手元のスプレッドシートに既存データがある場合は、このファイルをテンプレートとして
     列構成・ヘッダーだけ合わせても構いません。
2. **システムマスタの管理者メールアドレスを設定**
   - `Constants.gs` の `SYSTEM_ADMIN_EMAILS` を、実際にシステムマスタ（ロゴ・モデル写真・
     メール通知設定・担当者）へアクセスさせたいGoogleアカウントのメールアドレスに
     書き換えてください（配列、複数人可）。ここは担当者マスタと異なりコード上でのみ
     変更でき、画面からは変更できません。
3. **claspでのデプロイ**
   ```bash
   npm i -g @google/clasp
   clasp login
   clasp create --type webapp --title "販売可能リスト" --rootDir vehicle-order-app
   cd vehicle-order-app && clasp push
   ```
4. **スプレッドシートの紐付け**
   - 上記1で用意したスプレッドシートの「拡張機能」→「Apps Script」からスクリプトエディタを開き、
     コンテナバインドのスクリプトとして本プロジェクトのファイル一式を配置します（コンテナバインド
     であれば `SheetService.gs` の `getSpreadsheet_()` はそのまま動作します）。
     スタンドアロン運用する場合は `getSpreadsheet_()` を対象スプレッドシートIDでの `openById`
     に変更してください。
5. **トリガー設定**
   - 上記1で方法A（SetupService）を使った場合、トリガーは `setupSpreadsheet_()` の実行時に
     設定済みです。方法Bの場合は、GASエディタから `setupTimeDrivenTriggers_()` を一度だけ
     手動実行してください（Hold期限チェック・5分毎）。
   - 既に運用中のスプレッドシートを使う場合、コミッション列の先頭0が消えてしまっている
     ことがあれば `formatCommissionColumnsAsText_()` も一度だけ手動実行してください
     （今後の入力分から先頭0が保持されます。既に消えてしまった値は手入力し直しが必要です）。
6. **Webアプリとして公開**
   - `clasp deploy` または GASエディタの「デプロイ」→「ウェブアプリ」。
   - **重要**: 担当者のログイン連携（「ログイン連携について」の項を参照）を使うには、
     デプロイ設定で「実行するユーザー」を **アプリにアクセスするユーザー** にし、
     「アクセスできるユーザー」を **同一Google Workspace組織内**（または利用者を個別指定）
     にしてください。「自分」のまま・「全員（匿名可）」のままだと担当者が正しく判定されません。
7. **設定画面での初期設定**
   - 上記2で`SYSTEM_ADMIN_EMAILS`に登録したメールアドレスでログインし、Webアプリの
     「設定」タブ→「システムマスタ」から、ロゴ・モデル写真（ホーム画面）を必要に応じて
     登録し、Hold登録時／受注確定時／システムエラー時のメール通知先を登録してください
     （通知先未設定の場合、メール通知はスキップされます）。Google Chatへも通知したい
     場合は、同じカードの「Google Chat通知先（Webhook URL）」にWebhook URLを登録して
     ください（未設定の場合はGoogle Chatへの通知はスキップされ、メール通知には
     影響しません）。
   - 同じく「システムマスタ」の担当者（最大30人）に、各担当者の**拠点・名前・
     Googleアカウントのメールアドレス**を登録してください。ここに登録されていない
     メールアドレスでログインした人は、Hold登録・受注確定・Hold解除ができません。
   - テーマ（配色プリセット）は「テーマ」グループから、管理者以外の利用者でも変更できます。

## テスト

正規化）を Node.js の `vm` サンドボックスで検証します。
